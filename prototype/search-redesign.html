猫爪影视 · 搜索页 · 方案 A（遥控器优先 · 支持首字母）

横屏单套布局，手机 / 电脑 / 电视共用。已按你的要求选方案 A（左键盘 + 右快捷区）， 并加入片名首字母搜索。下面先把 TVBox 源码的实际情况讲清楚 —— 结论和直觉不太一样。

TVBox 源码调研结论

与直觉不同

你让我看 TVBox 是怎么实现的。我查了 sourceCode-ccc25f6 的搜索相关代码， 结论是：TVBox 没有本地拼音库，也没有首字母匹配。它的字面证据如下。

类 / 文件实际做了什么结论
SearchKeyboard.java 27~38 键的字母键盘：["远程搜索","删除","A".."Z","1".."0"]， 用 GridLayoutManager(6) 铺格，前两项各占 3 列 键盘是字母顺序，不是 QWERTY
PinyinAdapter.java 整个类只有 17 行：BaseQuickAdapter<String>， convert() 里就一句 setText(tvSearchWord, item) 名字骗人 —— 它只是个字符串列表 adapter，没有任何拼音逻辑
SearchActivity.loadRec() 调用腾讯视频在线接口 tv.aiseet.atianqi.com/…/get_search_smart_box， 把结果塞进"猜你想搜" 拼音联想靠在线接口，本地不算
SearchActivity.searchData() 唯一的结果质量控制：isHighMatchSearchResult() —— 去掉空白后 video.name.startsWith(searchTitle)，命中的优先展示 是前缀匹配原文，与拼音无关
FastSearchActivity 跨源并发搜索 + SEARCH_THREAD_COUNT=6 分批 + 10s 单站超时 + 分词过滤 （mGridViewWordFenci） 可复用的是调度策略，不是拼音
app/build.gradle 搜 pinyin 命中 0 条 —— 没有任何拼音依赖 确认无本地拼音方案
💡
所以「TVBox 怎么做的」这个问题的答案是：它没做。
TVBox 靠腾讯的在线联想接口把用户输入的拼音转成中文关键词（接口内部有拼音库）， 自己完全不实现拼音。这条路我们不能照抄 —— 依赖第三方接口，随时可能失效， 而且我们之前已经清理过这类外部依赖。
所以首字母搜索需要我们自己做。好消息是：在我们的架构下，有个比 TVBox 更干净的做法。
键盘布局（按你的要求）：左 QWERTY 字母 / 右小键盘（numpad）数字。
字母区是标准 QWERTY：QWERTYUIOP / ASDFGHJKL / ZXCVBNM， 行 2 缩进半个键、行 3 缩进一个半键，与物理键盘完全一致。
数字区是标准小键盘：7 8 9 / 4 5 6 / 1 2 3， 末行 0 / ⌫ / 搜索 —— 0 在最左（同物理小键盘），搜索在最右（同 Enter 位）。
两区行数虽不同（3 vs 4），但统一给定总高、行高按比例均分 → 底边天然对齐。
为什么最终选 QWERTY 而不是 TVBox 的「字母顺序」。 TVBox 用的是 A→Z 顺序网格，理由是"遥控器上视觉扫描可预测"。 但你的要求是 QWERTY，而且这个选择同样站得住：物理键盘与手机输入法的肌肉记忆是真实存在的， 用户在电视上搜索时往往是一边看手机/电脑回忆片名、一边按遥控器， 此时 QWERTY 的位置感能直接复用。两种都有道理，按你的选择来。
末行排布：0 在最左、⌫ 居中、搜索 在最右。理由：
· 0 必须贴左——物理小键盘的 0 是「宽键靠左」，把它放中间会破坏肌肉记忆 （你指出这点是对的，初版放中间是错的）；
· 搜索放最右，对应物理小键盘的 Enter 位，且它是这一行的收尾动作；
· 通栏长按钮在电视上视觉上很蠢，而且它只在"本地没命中要转跨源搜索"时才用得上；
· 首字母命中时根本不用按它——候选里直接 OK 进详情，这是主路径。
「清空」并入长按 ⌫（长按删除全部）——单独占一格不值，且长按是通用习惯。

首字母搜索：我们的做法

推荐

关键思路：不去做「拼音 → 汉字」的转换（那需要完整拼音库 + 汉字候选，正是 TVBox 绕不开才用在线接口的原因）。 改做「本地片名索引 → 反算首字母」 —— 只需对已知片名算首字母，不需要拼音反查。

步骤做法数据量
① 攒本地片名索引 用户浏览过（首页/分类/搜索）的片名写进本地索引，带 sourceKey/itemId/cover。 已有现成存储：VideoDatabase（SQLite） 几乎为零（复用现有库）
② 片名 → 首字母 需要一个「汉字 → 拼音首字母」映射。见下方三个方案 见下表
③ 输入即匹配 用户输入 lr → 在索引里找首字母以 lr 开头的片名 （流人=lr、流人第五季=lrdwj） 纯内存，微秒级
④ 命中即进详情 候选直接给影片（不需要再走一次网络搜索）→ OK 进详情页 零网络
⑤ 兜底 本地没命中 → 把输入当关键词走现有 SearchAsync 跨源搜（覆盖索引里没有的新片） 复用现有逻辑
为什么这比 TVBox 的路子好。 首字母命中时直接给出影片并跳详情，省掉了 TVBox「转汉字 → 再拿去搜」的两跳。 而且完全离线、瞬时响应、无第三方依赖。代价是只覆盖用户浏览过的片名 —— 但这恰好符合遥控器的使用场景（遥控器上不太会搜陌生的新片名）。

「汉字 → 首字母」的三种取法（需你拍板）

方案做法体积 / 依赖准确度
A · GB2312 区位码
推荐		 GB2312 一级汉字（3755 字）按拼音排序，用码值落在哪个区间判断首字母。 只需 26 个边界常量，零数据表 约 30 行代码
+ System.Text.Encoding.CodePages		 常用字 ~98%（生僻字/多音字偏差）
B · 内嵌首字母表 把 3500 常用字按 26 个首字母分组，内嵌为 26 个字符串常量 约 12 KB 源码
零依赖		 与 A 相当，可控（可手工补字）
C · 在线联想接口 TVBox 同款，调腾讯接口拿中文关键词 零本地数据 依赖第三方，随时失效
我的建议是 A。它不需要维护数据表、不需要手工补字，26 个边界常量是业界用了几十年的成熟做法。 唯一成本是要加 System.Text.Encoding.CodePages 包（官方包，几十 KB）。 如果你不想加包，就选 B。不建议 C：我们已经清掉过一批外部依赖，不该再加回一个。

筛选态：选中某站后只显示该站结果，顶部留一行「正在显示 X 的 N 个结果」 与返回「全部」的提示。焦点在筛选条时 ←→ 切站、↓ 进网格。
站点筛选的三个设计要点。
① 只列「本次真有结果」的站点，不是把所有订阅站都铺出来 —— 搜一部片，20 个站里可能只有 6 个有货， 把没货的列出来只会制造噪音。
② 每个 chip 带条数（6v电影 7），用户一眼看出哪个站资源多，不用逐个点进去看。
③ 正在搜的站显灰并标「搜索中…」（截图里的「🔒荐片」）—— 跨源搜索是增量上屏的， 后到的站会出现新 chip；明确标出"还在搜"比让用户以为漏了更诚实。
筛选条与「全选/反选」的区别。TVBox 的 SearchCheckboxDialog 是搜索前选站点 （决定搜哪些站，需要用户在搜索前做配置）；我们这个是搜索后过滤已有结果 （零配置、即点即见效）。两者目的不同：前者省时间，后者帮用户挑源—— 同一部片不同站画质/线路不同，这是用户真正关心的。
两者不冲突，可以都要（搜索前的站点配置放设置页）。

需要你拍板 4 件事：
① 汉字转首字母用方案 A（GB2312 区位码，需加官方包）还是 B（内嵌 3500 字表，零依赖）？
② 搜索历史要不要一起做？（TVBox 有，我们没有）
③ 首字母索引：只在浏览时被动攒（简单），还是额外在设置里加「重建索引」？（更可控）
④ 手机端是否也显示虚拟键盘？我建议不显示（系统输入法更好用），只在 TV/无物理键盘时启用。
