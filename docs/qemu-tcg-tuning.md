# QEMU TCG 调参实测：能拿回多少性能（2026-09-21）

> 本文回答一个问题：**不动架构、不换硬件，只调 QEMU 参数，能找回多少性能？**
> 全部数据来自同一台机器上的 A/B 交叉轮转实测，方法可复现（附录给了脚本）。

## 0. 结论摘要

| 问题 | 答案 |
|---|---|
| 调参有收益吗 | **有，但只是百分比级，不是数量级** |
| 最优组合 | `-cpu cortex-a76 -accel tcg,tb-size=256,split-wx=off` |
| 收益 | **约 1.22×**（中位数 67s → 55s，4 轮采样分布不重叠） |
| 换到引擎吞吐 | 19.5 MB/s → **约 23~24 MB/s**（推算，未做端到端吞吐实测） |
| 生产现状 | `QemuHostRuntime` **一个 `-accel` 参数都没传**，全是默认值 |
| vCPU 数 | **不要按宿主核数放大**：实测峰值在 2~4，12 核比 4 核慢 40%+（见 §6） |
| 值不值得改 | **值得**（一行改动、零风险），但**别指望它解决跨架构问题** |

**关键认知**：这 22% 是在 `2.9%` 那个数量级内部挤出来的。跨架构翻译的天花板没变 —— 真正归零的路只有 ARM64 宿主（见 `qemu-engine-performance.md` §7）。

---

## 1. 生产基线（读的是正在运行的进程命令行，不是文档）

```
-M virt -cpu max -m 5120 -smp 4 -nographic -L share
-kernel pkg_kernel -initrd pkg_initrd.gz
-append "console=ttyAMA0 rdinit=/init loglevel=4"
-netdev user,id=n0,hostfwd=tcp:127.0.0.1:20092-:20080
-device virtio-net-pci,netdev=n0
-drive file=.../storemain.img,if=none,id=hub0,format=raw,cache=unsafe
-device virtio-blk-pci,drive=hub0
-monitor tcp:127.0.0.1:18090,server,nowait
```

⇒ **没有任何 `-accel tcg,...`**，`tb-size` / `split-wx` / `thread` 全部走默认值。

## 2. 方法（为什么这么测）

不干扰正在运行的实例、也不依赖引擎的网络行为，做法是：

1. 从 `pkg_initrd.gz` 里取出 guest 的静态 ARM64 `busybox`（**与被测引擎运行在同一个 guest 内核上**）；
2. 用 Python 生成一个**最小 initramfs**（busybox + 基准脚本 + 64MiB 零文件），只做三件固定的事；
3. QEMU **不加网络、不加磁盘、不加 monitor** ⇒ 不可能碰到 `18080`／`20080`，不会干扰生产实例；
4. **交叉轮转**（A/B/C… 轮着跑，再重复多轮）取中位数 —— 单轮顺序跑会被机器负载漂移污染（见 §5）。

三个基准负载：

| 编号 | 内容 | 性质 |
|---|---|---|
| B1 | busybox `sh` 里 200 万次算术循环 | 最坏情况（解释器：间接分支 + 助手调用多） |
| B2 | md5 2 GiB（32×64 MiB 零） | 最好情况（紧凑循环、TB 复用率高） |
| B3 | sha256 1 GiB（16×64 MiB 零） | 介于两者之间 |

> B1 与 `qemu-engine-performance.md` §2.1 的样本同形，可与那条 `59.6s` 对照。
> **注意**：本文所有绝对秒数是**本机嵌套虚拟化环境**下的值，只用于互相比较。

## 3. 结果

### 3.1 主结果（第三轮：每配置 4 次交叉采样，机器空闲）

| 配置 | B1 四次采样 (s) | 中位数 | 相对基线 |
|---|---|---|---|
| **A 生产基线** `-cpu max` | 70 / 60 / 62 / 67 | **67** | 1.00× |
| D `-cpu cortex-a76 -accel tcg,split-wx=off` | 58 / 56 / 61 / 54 | 58 | 1.16× |
| **G `-cpu cortex-a76 -accel tcg,tb-size=256,split-wx=off`** | 56 / 54 / 54 / 55 | **55** | **1.22×** |

G 的分布（54–56）与 A 的分布（60–70）**完全不重叠** ⇒ 这个差异是真实的，不是噪声。

### 3.2 第二轮（每配置 2 次）方向一致

| 配置 | B1 | 中位数 | 相对 |
|---|---|---|---|
| A `-cpu max` | 65 / 59 | 62 | 1.00× |
| B `-cpu max -accel tcg,split-wx=off` | 66 / 78 | 72 | 0.86× ❌ |
| C `-cpu cortex-a76` | 59 / 60 | 59.5 | 1.04× |
| D `-cpu cortex-a76 -accel tcg,split-wx=off` | 47 / 57 | 52 | 1.19× |
| E `-cpu max,sve=off,sme=off` | 58 / 63 | 60.5 | 1.02× |
| F `-cpu max -accel tcg,tb-size=64` | 71 / 85 | 78 | 0.79× ❌ |

### 3.3 得出的三条规律

1. **`split-wx=off` 单独用没用，甚至更差**（B = 0.86×）；但配上 `cortex-a76` 就有效（D = 1.16×）。
   合理机制：`-cpu max` 打开了 SVE/SVE2，翻译块占用大得多，`split-wx=off` 换来的空间收益被吃掉；
   换到无 SVE 的 `cortex-a76` 后这笔交易才划算。
2. **`tb-size` 不是越大越好**：512 → 0.86×（第一轮还测到 0.81×），64 → 0.79×，而 **256 → 全场最佳**。
   默认 32 MB 附近偏小，但盲目放大反而伤缓存局部性。
3. **`-cpu max` 本身就是负担**：C（`cortex-a76`，无 SVE）与 E（`max` 但关掉 SVE/SME）都比 A 快，
   两者幅度相近（1.04× / 1.02×，在噪声内）⇒ 收益主要来自**关掉 SVE**。

### 3.4 CPU 能力兼容性（决定 `cortex-a76` 能不能上生产）

用同一个 guest 内核 dump `/proc/cpuinfo` 对比：

```
-cpu max        : fp asimd evtstrm aes pmull sha1 sha2 crc32 atomics fphp asimdhp cpuid
                  asimdrdm jscvt fcma lrcpc dcpop sha3 sm3 sm4 asimddp sha512 sve asimdfhm
                  dit uscat ilrcpc flagm ssbs sb paca pacg dcpodp sve2 ... (一大堆)
-cpu cortex-a76 : fp asimd evtstrm aes pmull sha1 sha2 crc32 atomics fphp asimdhp cpuid
                  asimdrdm lrcpc dcpop asimddp
```

`cortex-a76` 提供了 **NEON / AES / PMULL / SHA1 / SHA2 / CRC32 / LSE atomics / FP16 / dotprod** ——
这正是 2015~2018 年 Android arm64 库（含 `libxl_thunder_sdk.so`）会依赖的全部能力。
缺的只有 SVE / SVE2 / i8mm / bf16 这类**它不可能用到**的新扩展。

### 3.5 真实引擎功能验证（不是只看 CPU 跑分）

用**真的** `pkg_initrd.gz`（含真实迅雷引擎）各跑 200 秒固定窗口：

| 指标 | 生产参数 `-cpu max` | 候选参数 `cortex-a76 + tb256 + split-wx=off` |
|---|---|---|
| Kernel panic | 无 | 无 |
| `dns-hook` 次数 | 23 | **23** |
| TCP / UDP 行数 | 3 / 2 | 3 / 2 |
| `insmod` 成功数 | 4 | 4 |
| `error` 行数 | 7 | 7 |
| harness 启动 | 1 | 1 |
| **控制台行数（同窗口）** | 241 | **1088** |

⇒ **里程碑完全一致**（同样的 DNS 解析次数、同样的网络连接、无 panic、错误数相同），
而候选组在同样的墙钟时间内**推进了 4.5 倍的日志量** —— 与"CPU 更快、同一窗口内跑得更远"相符。

> ⚠️ 这是**功能等价性 + 推进速度**的证据，**不是吞吐基准**。
> 同一磁力的 peer 情况会随时间变化，`241 vs 1088` 不能当倍率读。

## 4. 建议的改动

`CatClawVideo.Core/Services/QemuThunder/QemuHostRuntime.cs` 的启动参数：

```diff
-"-M", "virt", "-cpu", "max", "-m", "5120", "-smp", SmpCount.ToString(), "-nographic",
+"-M", "virt", "-cpu", "cortex-a76", "-m", "5120", "-smp", SmpCount.ToString(), "-nographic",
+"-accel", "tcg,tb-size=256,split-wx=off",
```

优先级建议：**先只上 `-cpu cortex-a76`**（收益的大头在这里，且是纯 CPU 型号选择，语义最直观）；
`-accel tcg,tb-size=256,split-wx=off` 一起上也可以，它把 1.16× 推到 1.22×。

⚠️ 上线前必须做的验证（本次没做）：
1. **真实磁力边下边播**一次，确认文件列表解析、起播、seek 都正常（本次只验证到 200 秒窗口）；
2. `split-wx=off` 会关闭 QEMU 的 W^X 保护 —— 本地 guest 可接受，但要写进注释说明这是有意的取舍。

## 5. 一个方法论警告（对已有结论也成立）

第一轮顺序测量给出了**完全错误**的结论：

| | 第一轮（顺序，机器上有另一个 QEMU 在跑） | 第三轮（交叉轮转，机器空闲） |
|---|---|---|
| `split-wx=off` | 59s vs 基线 74s ⇒ 看起来 **+25%** | 66s vs 65s ⇒ **无差异** |
| 基线重复测量 | 74s → 68s（**漂移 8%**） | 60~70s（**同一配置内波动 10s**） |

⇒ **同一配置的run-to-run波动可达 ±10%**。这有两个含义：
1. 本机做任何 QEMU 性能对比，**必须交叉轮转 + 多轮取中位数**，顺序单跑会得出假结论；
2. `qemu-engine-performance.md` 里那些单次测量的绝对数字（19.5 / 40.8 / 38.1 MB/s）
   同样带这个量级的不确定度；**相对结论（差 2×、差 20×）仍然成立，但别把个位数百分比当准**。

## 6. vCPU 数量：加核到底有没有用？（2026-09-21 补测）

> 起因：想「让 QEMU 自适应使用本机所有核心」。**实测结果反对这个方向。**

本机 12 逻辑核（6 物理核）。两个独立实验：

### 6.1 纯计算负载（并行 md5，每 worker 2 GiB）

总吞吐（两台交叉采样中位数）：

| vCPU | 1 | 2 | 4 | 6 | 8 | 12 |
|---|---|---|---|---|---|---|
| 总吞吐 MB/s | 292 | 512 | 910 | 1024 | 1170 | 1293 |
| 相对 1 核 | 1.00× | 1.75× | 3.12× | 3.51× | 4.01× | 4.43× |
| 并行效率 | 100% | 88% | 78% | 58% | 50% | 37% |

⇒ 纯计算**确实随核数单调增长**，但 4 核之后急剧衰减，12 核只有 4.43×。

### 6.2 ★ 真实引擎负载（引擎从宿主本地 HTTP 服务器下载，无外网、无 peer 波动）

方法：把生产 `pkg_initrd.gz` 的 `/init` 改成 URL 直链任务（跳过已失效的默认磁力），
宿主用 Python 起 HTTP 服务器（实测持续 296~348 MB/s，不是瓶颈），
guest 经 SLIRP 从 `10.0.2.2` 拉取 4 GiB 负载，读引擎自报的 `mDownloadSpeed`。
参数与生产一致（`-m 5120`），只变 `-smp`。

| vCPU | 引擎速度（10 次采样中位） | 相对 1 核 |
|---|---|---|
| 1 | 16.2 MB/s | 1.00× |
| 2 | 20.8 MB/s | 1.28× |
| **4** | **22.2 / 17.6 MB/s（两次重复）** | 1.37× / 1.09× |
| 8 | 19.9 MB/s | 1.23× |
| **12** | **12.7 MB/s** | **0.78×** ❌ |

⇒ **引擎在 2~4 vCPU 达到峰值，超过 4 之后不再增长，到 12 反而比单核还慢 22%。**

### 6.3 结论：不要按宿主核数放大 `-smp`

1. **本机 12 逻辑核 = 6 物理核**。`-smp 12` 让 12 个 vCPU 线程去抢 6 个物理核，
   再加上 SLIRP（单线程）、宿主 HTTP 服务器、Windows 自身 ⇒ 严重超订，引擎被饿死。
2. 引擎的线程模型（网络 + 分片 + 加密）在 4 vCPU 附近就饱和了，**再加核只是增加争用**：
   TCG 的翻译块缓存与翻译锁是全局共享的，vCPU 越多，撞锁越频繁。
3. 这条结论**修正了本文档 §3.3 之前的推测**：当时我以为"4→8 变慢是老参数下的现象"，
   实测表明**在调优参数下依然成立** —— 与 `qemu-engine-performance.md` §2.3
   原先记录的「`smp` 4→8 反而 19.5→15.3 MB/s」完全一致。**那条老结论是对的。**

**建议的规则（按宿主核数自适应，但设上限）：**

```csharp
// 实测引擎峰值在 2~4 vCPU；按宿主核数减半，且硬上限 4，下限 1。
// 不能取「所有核心」——12 vCPU 实测比 4 vCPU 慢 40%+。
SmpCount = Math.Clamp(Environment.ProcessorCount / 2, 1, 4);
```

| 宿主逻辑核 | 8 | 12 | 16 | 4 | 2 | 1 |
|---|---|---|---|---|---|---|
| 建议 `-smp` | 4 | 4 | 4 | 2 | 1 | 1 |

### 6.4 ⚠️ 顺带发现：`thread=multi` 是最大的 TCG 杠杆（4.1×）

纯计算基准里加 `-accel tcg,...,thread=single` 强制单线程翻译：

| 配置 | 总吞吐 |
|---|---|
| 默认（MTTCG 自动开启） | **910 MB/s** |
| 强制 `thread=single` | **221 MB/s** |

⇒ 差距 **4.1×**，比 `tb-size`/`split-wx` 的 1.22× 大一个量级。
好消息是 **QEMU 对 aarch64 + smp>1 默认就开 MTTCG**，所以现在没踩这个坑；
但**任何 `-icount` / `thread=single` 类改动都会一次性抹掉 4 倍性能**，
在 `QemuHostRuntime` 里值得写一句注释钉住。

### 6.5 测量噪声提醒

同一配置（`smp=4`）相邻两次重复：**22.2 / 17.6 MB/s（差 21%）**。
所以本文所有引擎速度的比较，**只能看趋势和量级，不要抠个位数百分比**；
`1 vs 2 vs 4 vs 8` 之间的差异大多落在噪声内，
唯一统计上干净、可信的结论是 **「12 核明显更差」** 与 **「不要超过 4」**。

## 7. 多实例并发实测（2026-09-21 补充）

> 起因：§6 的单任务结论被质疑 —— 「单任务当然用不满 12 核，真实使用里是并行负载才对」。
> 于是直接跑多实例：**N 个 QEMU guest 同时下载，各自一个真实引擎任务**。

方法：同一台本机，N 个 guest 同时从宿主本地 HTTP 服务器拉 4 GiB 负载，
读各自引擎自报的 `mDownloadSpeed`。`-m 2048`（本机可用内存只有 10.8 GB），
调优参数一致，只变实例数与每实例 `-smp`。

| 配置 | 每实例速度 | **合计** | 相对单实例 |
|---|---|---|---|
| 1 实例 × `smp=4` | 29.8 | **29.8** | 1.00× |
| 2 实例 × `smp=4` | 20.0 / 18.1 | **38.1** | **1.28×** |
| 2 实例 × `smp=2` | 14.7 / 14.4 | **29.1** | 0.98× |
| 3 实例 × `smp=4` | 13.3 / 13.7 / 14.8 | **41.8** | **1.40×** |

### 7.1 结论

1. **质疑方部分正确**：并行实例确实能提高**总吞吐**（29.8 → 38.1 → 41.8），
   说明宿主的多核不是白给的。
2. **但收益严重次线性**：**3 倍的工作量只换来 1.40× 的总吞吐**，
   而且每实例从 29.8 掉到 13.8（**-54%**）。原因是本机 12 逻辑核只有 **6 物理核**，
   2~3 个实例的 vCPU 线程（8~12 条）已经超订。
3. **★ 关键反证：`smp=2` 反而更差。** 2 实例下把每实例 vCPU 从 4 降到 2
   （总线程 8→4，本该减少争用），合计却从 **38.1 掉到 29.1**。
   ⇒ **限制每实例速度的是它自己的 vCPU 数，不是宿主争用**；
   引擎需要 ~4 个 vCPU 才能喂饱它内部的线程池。
4. ⇒ **`-smp` 该保持 4/实例，不随宿主核数放大。** 多实例时由操作系统调度器去分时即可，
   不需要（也不应该）手动把单实例的 `-smp` 调大。把单实例调到 12 仍然是净损失（§6.2）。

### 7.2 ⚠️ 意外发现：guest 内存大小可能比 TCG 参数影响更大

同一个 `smp=4` 单实例：

| guest 内存 | 引擎速度 |
|---|---|
| `-m 2048` | **29.8 MB/s** |
| `-m 5120`（生产值） | 22.2 / 17.6 MB/s |

差约 **1.5×** —— 比 `tb-size`/`split-wx` 那 1.22× 还大。合理机制：TCG 要维护
guest 物理地址→宿主地址的映射与页表模拟，guest RAM 越大，这部分开销越大。

⚠️ **但这组对比混入了 run-to-run 噪声（±21%）与不同批次的机器状态，不能当结论。**
如果这条成立，它是目前发现的**最大单体杠杆**，值得单独做一次交叉轮转 A/B 验证。
生产用 `-m 5120` 的理由是「要容下 `/thunder-data` 的 3500m tmpfs」——
真要下调内存，得先确认把 tmpfs 一起调小不会影响长任务。

## 8. CPU 亲和性（vCPU 绑定）：实测**负收益**（2026-09-21 补充）

> 起因：「虚拟机可以绑定核心减少 CPU 之间的跳转」——这个记忆本身没错，
> 是标准虚拟化优化（减少跨核迁移、保住 TB 缓存与 L2/L3 局部性）。
> **但在 Windows + QEMU TCG + 本机（嵌套虚拟化）这个组合上实测是负收益。**

方法：把 QEMU 进程（`ProcessorAffinity` / `SetProcessAffinityMask`，对进程内所有线程生效）
绑到不同规模的核心集，其余参数与生产一致（`-cpu cortex-a76 -m 5120 -smp 4
-accel tcg,tb-size=256,split-wx=off`），每档 210 s，读引擎自报 `mDownloadSpeed`。
宿主 12 逻辑核 = 6 物理核，单 CCX。

| 配置 | 亲和性掩码 | 引擎中位 | 相对基线 |
|---|---|---|---|
| 01 基线（不绑定，生产现状） | — | **36.6 MB/s** | 1.00× |
| 02 绑 12 逻辑核（= 全部） | `0xFFF` | 24.2 | **0.66×** ❌ |
| 03 绑 8 逻辑核 = 4 物理核 | `0xFF` | 28.6 | 0.78× ❌ |
| 04 绑 6 逻辑核 = 3 物理核 | `0x3F` | 26.3 | 0.72× ❌ |
| 05 绑 4 逻辑核 = 2 物理核 | `0xF` | 26.9 | 0.73× ❌ |
| 06 不绑定 + 进程优先级 `High` | — | 34.3 | 0.94×（噪声内） |
| 07 基线重复（漂移对照） | — | **35.3** | 0.96× |

### 8.1 结论

1. **绑定一律变慢**（0.66×~0.78×），**且与绑几个核无关** —— 绑 4 核（26.9）与绑 12 核（24.2）
   几乎一样，而绑 12 核**在语义上等价于不绑**。⇒ 惩罚来自「施加了亲和性约束」这个动作本身，
   不是核心数不足。
2. **不是噪声**：漂移对照 01=36.6 / 07=35.3（差 4%），而绑定组稳定聚集在 24~29。
3. **进程优先级 `High` 基本中性**（0.94×，在噪声内）—— 想要"少被打断"的话，设优先级比绑核划算。

**机制推断（未直接测量每核占用，故标为推断）**：Windows 的 `SetProcessAffinityMask` 不只是
"限定可用集合"，还会让调度器对该进程改用更受约束的放置策略。QEMU 的 vCPU 线程 + SLIRP +
IO 线程本来靠调度器自由迁移来避让瞬时热点（宿主 HTTP 服务器、系统进程等），硬约束后容易撞堆；
也可能连带关掉了 core parking / 频率提升相关启发式。

### 8.2 为什么这台机器上"迁移"本来就不贵

本机是 **Proxmox 上的 QEMU 虚拟机**（见 `qemu-engine-performance.md` 附录 B），
所谓"物理核"其实是 Proxmox 的 vCPU，下面还有一层调度器。
⇒ 客户机看到的"迁移"，在物理层面可能只是同一物理核上的 vCPU 切换。

**所以这条结论要带前提**：在**裸机**上跑（非嵌套虚拟化）时，亲和性的收益/代价可能完全不同，
值得重测。当前**不建议在生产里加绑定**；真要试，也应该做成设置项而不是写死。

### 8.3 ⚠️ 批次间绝对数值不可比（重要）

同一配置 `-cpu cortex-a76 -m 5120 -smp 4`：

| 批次 | 引擎中位 |
|---|---|
| §6.2 那批（vCPU 曲线） | 22.2 / 17.6 MB/s |
| 本批（亲和性矩阵） | **36.6 / 35.3 MB/s** |

**同一配置在不同批次之间差了 1.7×**，远超任何单个调参收益。
⇒ 本文所有绝对 MB/s **只能在同一次批量运行内部互相比较**（所以每个矩阵都带漂移对照）。
跨批次的"某个配置更快"结论一律不成立——包括 §3 那个 1.22×，
它的可信度来自**同批次 4 轮交叉采样、分布不重叠**，而不是来自绝对数字。

### 附录 B：避坑记录

1. **`Start-Process` 会把 `-ArgumentList` 拍平成一条命令行** ⇒ `-append` 的值必须自己带引号
   （`'"console=ttyAMA0 rdinit=/init loglevel=4"'`），否则 QEMU 把 `rdinit=/init` 当成一个文件名，
   报 `Could not open 'rdinit=/init'` 并瞬间退出（一轮矩阵 1 秒钟全废）。
2. **基准 guest 不要加 `-netdev`/`-drive`/`-monitor`** —— 加了就可能碰到生产的 18080/20080。
3. `-accel tcg,help` 查不到选项列表（这个 build 没暴露 `help` 属性），
   但 `tb-size` / `split-wx` 都实测可用。
4. 基准结果要**校验哈希值**（脚本里打印 `CHECK=`），否则"哈希太快"其实是文件没读到。
