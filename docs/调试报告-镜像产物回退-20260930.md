# 镜像产物回退：磁力「点了没下文」的产物侧根因（2026-09-30 夜）

> 接手人第一份该读的**事故记录**。结论先说：**爬虫桥与磁力链路的代码都是好的，
> 坏的是打包产物** —— 部署的 `art_initrd_x64.gz` 里 `/init` 缺整段迅雷段、且两个桥 dex 是旧版。
> 已经修好管线并加了装配期自检；本文记录证据、根因、修法与遗留。

## 一、怎么发现的

跑 T5（连续 10 分钟长跑）时**台架 M1 直接失败**：

```
FAIL  M1 VM 起来且 harness 回连控制口
      ⟵ 失败原因：迅雷 harness 180s 未回连控制口（initrd 里没有迅雷段 / harness 起不来）
PASS  M1b 合并 VM 里爬虫桥仍在（没被迅雷段环境泄漏打死） ⟵ 桥 socket 已连上 18600
```

**爬虫桥活着、迅雷 harness 不在** —— 正是《磁力播放链路》报告 §2「缺陷 3」的指纹。

## 二、证据链（逐层收敛）

**① guest 侧日志**：cmdline 里 `thunderport=18080` 在，但 init 跑完 virtio/binder 的 insmod
就直接进 artlaunch，**没有** `[init] binfmt arm64 已注册`、**没有** `[thunder] harness 监督循环已起`。

**② 拆镜像逐条比对**（`.zwork/initrd_cat.py`）：

| 条目 | 部署镜像（17:54 那版） | 应有版本 | 后果 |
|---|---|---|---|
| `/init` | **4,918B**，与 bootimg 产物逐字节相同 | 7,074B / 7,513B | 无迅雷段 → 磁力点了没下文 |
| `gb.dex` | **210,672B** | 222,756B | §7 网盘三层修复全丢 |
| `ui_stub.dex` | **7,393B 且内容含 `[thunder]`** | 122,992B | §2 缺陷1（verifier）修复全丢，且是被写坏的槽位 |

`ui_stub.dex` 里出现 init 文本，是**错位写入**的指纹 —— 顺着它找到了管线 bug。

**③ 时间线**：镜像 17:54:50 打出；注入器模板 `build_bootimg_inject.py` **20:13:25** 才被修好
（新增迅雷段插入 + ARM 库路径纪律），**但没人重打镜像** → 部署位一直停在坏产物上。

## 三、根因（两个，都在打包侧）

### 根因 1：注入器 ④b 段的**索引错位**（本次新修）

```python
# ④ 段（在 ④b 之前）
init_i = next(i for i, e in enumerate(merged) if e[0] == "init")
...
merged[init_i] = merged[init_i][:6] + (init,) + merged[init_i][7:]

# ④b 段：合并磁力资产时**重建了整个列表**（过滤同名 + 追加 36 条）
merged = [e for e in merged if e[0] not in tn] + thunder_entries
...
merged[init_i] = ...   # ← 仍用旧索引！列表已位移
```

后果三连（与 §二 的观察一一对应）：
1. 迅雷版 init 的**文本**被写进位移后落在这个下标上的条目 —— 实测是 `ui_stub.dex` 的槽位
   （所以它变成 7.5KB 且含 `[thunder]`）；
2. 真 `/init` 保持 ④ 段打完补丁、但**不含迅雷段**的版本（4,918B）；
3. 这个 bug 还会顺带毁掉被覆盖的那个条目。

**修法**：写回前**按名字重新定位** init（见 `build_bootimg_inject.py` ④b 段注释）。

### 根因 2：管线**继承 pristine 的旧 dex**

`build_bootimg_inject.py` 以 `art_initrd_x64_pristine.gz` 为底，pristine 里的 `gb.dex`
（210,672B）与 `ui_stub.dex`（134,956B）都会被原样带进产物；`bootimg_artifacts.cpio.gz`
只含 `system/javalib/**` 与 `data/dalvik-cache/**`，**不含根 dex**。
⇒ 打完之后**必须**再跑 `inject_dex.py` 换入当前 `JavaBridge/qemu-src/art/{gb.dex,ui_stub.dex}`。

## 四、修法与固化（本次落地）

| 项 | 内容 |
|---|---|
| 注入器 | 修 ④b 索引错位（`JavaBridge/qemu-src/tools/x86guest/build_bootimg_inject.py`） |
| **装配期自检** | 新增 `JavaBridge/qemu-src/tools/x86guest/check_image.py`：断言 init 含迅雷段/harness 拉起/`-Ximage` 补丁/反向后门、ARM 库路径只挂在 harness 命令行上（恰 1 处）、`gb.dex`/`ui_stub.dex` 与源码产物 md5 一致、无错位写入。**不过就不该部署** |
| 一条龙 | `.zwork/rebuild_gb.cmd` 重写为「重打 bootimg → 换当前 dex → 自检 → 部署」。旧版引用了**并不存在**的 `.zwork\init_new.sh`，跑到第 4 步就 `exit /b 4`（于是大家以为跑了重建，其实镜像没变），且它只注入现网镜像、不重打 bootimg |
| 忽略规则 | `.gitignore` 补 4 条：`art_initrd_x64_pristine.gz` / `bootimg_artifacts.cpio.gz` / `thunder_assets.cpio.gz` / `art_initrd_x64_bootimg.gz`（共 ~620MB 的中间件，原先未被忽略，`git add -A` 会误收，GitHub 单文件 100MB 会拒 push） |
| 自检的坑 | `check_image.py` 必须**归一 `./` 前缀**：bootimg 线与 inject 线写出的条目名一套带 `./`、一套不带，不归一会把好镜像误判成「init 不存在」 |

**自检双向验证**：拿留档的坏镜像（`.zwork/art_initrd_x64_broken_1754.gz`）跑 → **6 项 FAIL**
（含"错位嫌疑条目: `ui_stub.dex`"）；对新产物跑 → **12/12 PASS**。

## 五、修后实测（台架，宿主侧真跑）

```
PASS M0 取到真实磁力 159 字符
PASS M1 VM 起来且 harness 回连控制口          ⟵ 媒体口租约 18601
PASS M1b 合并 VM 里爬虫桥仍在                  ⟵ 桥 socket 已连上 18600
PASS M2 磁力展开出文件列表                     ⟵ 2 项（250/243MB）
PASS M3 拿到可播地址                           ⟵ 4.3s
PASS M4 起播出数据（≥64KB 且有容器头）          ⟵ HTTP 206 头=1a45dfa3…（Matroska）
PASS M5 拖动（中段 Range）不被空 206 骗过去     ⟵ HTTP 206 字节 65536
PASS M6 同磁力切文件                           PASS M7 暂停后重播
结果：9 通过 / 1 失败
```

唯一失败是 **T5 长跑**：`2.9min 读了 185.8MB（743 块，**平均每块 256.0KB**，最慢单块 0.0s）`
→ 第 744 块 `HttpIOException: response ended prematurely`，紧接着 guest 侧：

```
[thunder] [引擎] 合并模式：重启 guest 内迅雷 harness（EXIT → 监督循环拉起）
[thunder] [引擎] 外部 VM 已退出（爬虫桥重置/崩溃）——结束迅雷会话
[art-vm] [qemu] 已停止
```

⇒ **T5 是被「已知的偶发 native 崩溃导致 VM 退出」打断的**（见《磁力播放链路》§五.3 与 §10
登记的噪音），**不是**磁力/代理缺陷。反过来说：**平均每块 256.0KB（旧镜像 43.5KB）**
证明 §6.5 的短读修复现在**真的生效了** —— 而它在此之前一直"生效不了"，正因为 dex 是旧的。

## 六、一条重要纠偏：**不要**把 aarch64 那套反向搬进 x86

现场曾判断「aarch64 的 art 是完整体，x86 缺东西，不如整体搬过来」。实测结论相反：

- aarch64 两个镜像冻结在 **09-29 06:00/06:02**，其 `ui_stub.dex` 还是含 `android/graphics`
  的旧版（134,956B → 现 122,992B）；**§2 缺陷1 与 §7 网盘修复都不在里面**。搬过来 = 退回昨天。
- 「迅雷段」不是 aarch64 的遗产：aarch64 **纯桥** init（6,268B）没有它；aarch64 **合并** init
  （11,375B，zstd）才有，而 x86 的 init 就是它的移植版（**功能超集**：多 `binfmt`/`ndk_translation`/
  反向后门/APEX 环境变量）。
- 架构绑定、**不可搬**：`artlaunch`/`artlaunch.x64`、`proppreload.so`、`libart`、系统镜像
  （Android 9 arm64 ↔ Android 13 x86_64）、内核、`bootimg/*/arm64` 的 pre-oat/vdex。
  架构无关、可共用：dex、`bridge.jar`、`harness` + ARM 引擎资产（x86 靠 `qemu-aarch64-static` 跑）、
  init 的段落逻辑与纪律。

**⇒ 权威线是 x86 这条**：新东西都在这里，要固化的是它，而不是从 aarch64 搬。

## 七、遗留（按优先级）

1. **T5 那一格仍未绿**：需在一次**没有并发写镜像**的干净窗口重跑；若稳定在同一位置崩，
   则要把「VM 中途退出」当成**真缺陷**查（`%LOCALAPPDATA%\CatClawVideo.debug\qemu-console-art.log`
   + guest tombstone），而不是继续按"已知噪音"记账。
2. **两条镜像线在互相覆盖**：bootimg 线（`build_bootimg_inject.py` → 带 boot 提速补丁，init 7,513B）
   与 inject 线（`inject_dex.py` + `init_now.sh`，init 7,074B）都写出了**通过自检**的产物，
   且都会写同一对部署位。需要定一条为权威、另一条退役（否则"内容回退"会反复发生）。
3. **并发写入会毁掉台架**：本次 T5 重跑就撞上「镜像正在被写」→ guest kernel panic
   `Initramfs unpacking failed: incorrect cpio method used`。跑台架前除了关应用，
   还应确认**没有别的会话/脚本在重打镜像**。
4. `docs/调试报告-磁力播放链路-20260930.md` §9 的「磁力 11/0」是**旧镜像 `49f60c7…`** 上的数字，
   不代表 17:54 之后的任何一版镜像。

## 八、追加：同一类 bug 的第二处（basename 匹配）+ 并发重打污染了验证

### 8.1 三次 T5 里只有第一次可信

| 轮次 | 镜像状态 | 结果 |
|---|---|---|
| 1（21:12） | 我方部署 `b4420a`（自检 12/12） | **9 PASS / 1 FAIL**；T5 在 2.9min 被已知 VM 崩溃打断 |
| 2（21:19） | 被并发方改写中（21:24 落盘） | guest `Initramfs unpacking failed: incorrect cpio method` → kernel panic（读到半写文件） |
| 3（21:29） | 跑前 `3e900e` 稳定 30 秒，运行中 21:32:23 被改写 | 首次启动 `Failed to execute /init (error -13)`（EACCES，同因半写）→ 180s 判 M1 失败；**第二次启动才正常** |

**并发源判定**：最近 20 分钟内**只有镜像文件被改**（21:24:04、21:32:23，间隔约 8 分钟），
源码零改动 ⇒ 另一个会话在跑「重打镜像 → 部署」的循环。
**跑台架前除了关应用，必须确认没有别的会话在重打镜像**；否则结果一律不可信。
（本次靠 md5 金丝雀才发现：跑前记录的指纹与跑后不符。）

### 8.2 第二处同类 bug：替换项按 **basename** 匹配（已修）

`inject_dex.py`（.zwork）与仓库内的 `replace_initrd.py` 都用 `os.path.basename(name)` 匹配，
于是传 `init=…` 会**同时命中三个条目**、全部写成 init 文本：

| 条目 | 本应 | 21:32 那版镜像实测 |
|---|---|---|
| `init` | 7,074B 引导脚本 | ✔ 7,074B |
| `system/bin/init` | **2,337,688B** Android init 二进制 | ✘ **7,074B（被毁）** |
| `system/etc/init` | 0B 目录条目 | ✘ 7,074B |
| `data/dalvik-cache/x86_64/gb.dex` | 17,296B dex2oat 缓存 | 传 `gb.dex=` 时同样被覆盖 |

镜像**仍能启动**（PID1 是 cpio 根的 `/init`），因此**没有任何报错** —— 属静默毁产物。
`fix_thunder_env_leak.py` / `drop_verify_none.py` 都以 `init=…` 调它，所以每跑一次毁一次。

**修法**：改为「归一后的**完整路径**精确匹配」（`norm_path`：去 `./` 前缀与首尾 `/`），
打印被替换条目的**全名**（一旦有人改回 basename，日志里会立刻多出 `system/bin/init`），
未命中的 key 直接 `exit 2`。用 `pristine` 做干净基线双向验证：

```
修复前：init= 命中 3 条（init / system/bin/init / system/etc/init 全变 7,074B）
修复后：替换 init: 3679 → 7074 B ；共 2119 条目，替换 1 条（请求 1）
        system/bin/init 保持 2,337,688B 不动 ✔
```

**唯一有效那轮（镜像 `b4420a`，自检 12/12）的数字**：M0–M7 全过、平均每块 256.0KB、
T5 被 VM 崩溃打断在 2.9min —— 这条仍是**未结项**（见 §七.1）。

## 九、结项：干净窗口重打 + 原子部署后，**T5 通过，矩阵 10/10 全绿**

### 9.1 这一轮为什么可信

1. **安静窗口**：连续 90 秒观察，镜像指纹不变、无构建类进程、应用未跑；
2. **重打用修好的工具链**：`build_bootimg_inject.py`（索引已修）→ `inject_dex.py`（完整路径匹配）
   → `check_image.py` **12/12 通过**（init 7,513B 含迅雷段/`-Ximage`/反向后门、两个 dex 与源码一致、无错位写入）；
3. **原子部署**：先写同目录临时文件再 `Move-Item` 改名，避免任何人读到半写文件；
4. **md5 金丝雀**：跑前记录 `5b7b73f30f245630482b33a57a05af82`，**跑后完全一致** ⇒ 全程无并发写入。

### 9.3 这轮暴露的两个真实行为（都不是卡顿，但要跟进）

1. **harness 中途重启 4 次，读取零中断**：行 3729/4075/5893/9935 出现
   `[引擎] 合并模式：重启 guest 内迅雷 harness（EXIT → 监督循环拉起，引擎任务表清空）`，
   而相邻块的最大间隔仍是 **0.1s** —— 合并 VM 的「EXIT → 监督循环拉起」自愈确实在工作。
   （对比：§八.1 那轮是**整个 VM 退出**（`外部 VM 已退出` + `qemu 已停止`），那才是 T5 的真凶。）
   文件末尾的 `外部 VM 已退出 / 已停止` 是 T5 结束后的正常收尾，**别误读成崩溃**。
2. **`[proxy] 重定位 → X MB（播放器请求窗口外）` 出现 4120 次，平均块 11.0KB**：
   顺序读的播放器几乎每次都落在"已供出窗口"之外，于是每块都走一次 re-seek + KICK PREFETCH。
   本轮的判据是「单块不卡顿」（0.1s 达标），所以通过；但**预取窗口没有跟上顺序读**这一点
   与同镜像另一轮的 256KB/块形成明显反差，建议作为独立优化项（不是本次镜像问题）。
