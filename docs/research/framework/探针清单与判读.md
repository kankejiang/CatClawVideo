## 二、判读规则（跨探针的三条总线）

1. **"缺文件" vs "缺编排" 必须分开算**。本次全部差距里，只有 4 个 vendor HAL 二进制属于"缺文件"；
   其余（属性服务、trigger、服务管理、apex 挂载模式）都是"缺编排"——镜像里东西都在。
   判据：`audit_rc.py` 的缺失可执行数 + `probe_guest_runtime.sh` 的关键二进制行。
2. **参照系优先于源码推理**。凡"框架需要 X 吗"的争论，先在 108 上问一次运行时
   （`getenforce`、`ls /dev/__properties__`、`mount | grep /apex`、`getprop init.svc.zygote`）。
   本次两条既有结论就是这么被推翻的（SELinux 阻塞说、apex 缺内容说）。
3. **比较必须同判据**。`remote_probe.sh` 复用同一支 `audit_*.py`，只换 `--source/--prefix`；
   换判据的数字不许进矩阵。

## 三、探针自己的坑（都付过学费，写下来免得下次重踩）

- **cpio 的 4 字节对齐要按绝对偏移算**。按"条目内相对偏移"补位的写法会在第一条之后走歪，
  症状是**只解析出 1 个条目且不报错** —— 静默毁掉整份审计。（`cpioimg.iter_cpio` 已按
  `.zwork/inject_dex.py` 的绝对偏移写法实现。）
- **`waydroid shell` 里带管道/`$(…)` 的问句必须写成 `waydroid shell -- sh -c '…'`**。
  少了 `-- sh -c`，waydroid 自己的 argparse 会把参数吃掉，症状是 `unrecognized arguments`
  或整段返回空 —— 会被误读成"参照系也没有属性区"。
- **`scp -r 目录 目标:已存在的路径` 会变成目录套目录**，远端跑的还是上一版脚本。
  先 `ssh … 'rm -rf /tmp/t4probe'` 再 scp。（本次就跑了两次才发现。）
- **guest 里任何 adb shell 输出都要先滤掉 `[proppreload]` 行**：它每个新进程打一行
  `接管 Android 属性 API：161 条`，一次问多件事时输出会交错 —— 我第一次据此得出
  "`init`/`apexd` 不在 `/system/bin`"的**假结论**，滤掉后 7 个关键二进制全在位。
- **`apex-info-list.xml` 的属性名是 `moduleName` 不是 `package`**（第一版正则 0 命中，
  差点把"账本里没有 apex"写进矩阵）。
- **镜像里有 ≠ 运行时看得到**：`--source` 只查镜像，运行时必须另走 `probe_guest_runtime.sh`。
- **`env` 会吞掉输出**：Git Bash 里 `env python 探针.py > 文件` 得到的是 **exit=0 + 0 字节**
  （`env` 起 Windows 原生 python 时丢了继承的 stdout 句柄）。我据此差点判成"UTF-8 修复把探针修坏了"，
  普通 `python 探针.py > 文件` 一切正常 ⇒ **验收要看字节数，不能只看退出码**。
- **编码崩溃的正控制（修前 vs 修后）**：HEAD 版在 GBK 控制台下于 `cpioimg.py:172 table()` 抛
  `UnicodeEncodeError: 'gbk' codec can't encode '\u2714'`，exit=1、只落 407 B（修后同一支 2,211 B）
  ⇒ 审核说的"证据在首个特殊字符处被截断"是实测事实，不是推测。
- **镜像在被人实时重建**：本轮审计期间 `art_initrd_x64.gz` 换了三个 sha
  （`07daeec2` 362,396,900 → `be7a9307` 362,769,022 → `74531c46` 374,588,473），
  而**所有结构性数字（rc 69/79/212、属性表 161、APEX 6/6、framework 面 802/103/699）一个没变**；
  只有"运行日志计数"这类每启动都变的量跟着动 ⇒ 矩阵里那类数字要标"本次样本"，别当常量引用。

## 六、E2 怎么重跑（不依赖 adb，也不依赖 T1 在场）

```powershell
# 关应用（镜像被 QEMU user-mapped 占着，不关就复制失败）
taskkill /IM CatClawVideo.Maui.exe /F
python tools\b1-build\shadow_init.py                     # 开：默认 exec /system/bin/init second_stage
python tools\b1-build\shadow_init.py --child             # 诊断形态：init 当子进程，死了报退出码
python tools\b1-build\shadow_init.py --strip-seclabel    # 再摘掉 rc 里所有 seclabel（SELinux 无策略时用）
python tools\b1-build\shadow_init.py --off               # 关：一键回退（备份件 md5 已核对）
```
判据一律走串口：`%LOCALAPPDATA%\CatClawVideo.debug\qemu-console-art.log`，看 `[init]` / `init:` / `[E2]` 三种行。
两个必须知道的坑（都是这一轮实测踩出来的）：
1. 宿主 cmdline 是 `loglevel=4` ⇒ **优先级 >3 的 init 日志不上串口**；再加上 `/dev/kmsg` 的按进程限速
   （实测一次吞掉 28 行，表现为"一个字没留就重启"）。分发器里已经 `echo 7 4 1 7 > /proc/sys/kernel/printk`
   + `echo on > /proc/sys/kernel/printk_devkmsg`，自己另写探针时要照做。
2. 别用 `getprop` 的存在与否判断属性区 —— `/system/bin/getprop` 也在 `/system/bin/linker64` 软链那个坑里
   （init 的挂载命名空间之后 execve ENOENT），它报 0 行不等于区是空的；`ls /dev/__properties__ | wc -l` 才是独立证据。
