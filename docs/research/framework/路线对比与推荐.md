# 路线对比与推荐｜zygote / system_server 到底怎么落地

> 判据基线（先说清"成功"长什么样，否则三条路线都能自说自话）：
> **B1.2 达成 = guest 里 `init.svc.zygote=running` + `sys.boot_completed=1` + `pm install` 能装能起。**
> 参照系三条全中（`evidence/108-reference.txt` §0：`init.svc.zygote=running`、`sys.boot_completed=1`、
> `apexd.status=ready`、145 条 `init.svc.*`）；我们三条全空（`evidence/guest-runtime.txt`：
> `init.svc.*` 0 条、`sys.boot_completed` 空、属性区 0 项、PID1 = `/bin/busybox sh /init`）。

## A｜真 init 路线（把镜像里已有的 init 变成 PID1）

**不是"移植 init"** —— `system/bin/init` 2,337,688 B 已在镜像里，运行时也在位（`guest-runtime.txt` 的
`ls -l` 实测）。要改的是五件事：

| 要改什么 | 依据（数字） |
|---|---|
| ① PID1 换成 `/system/bin/init`，我们的 `/init` 降级为 `import` 进来的 extra rc | 现 PID1 是 busybox sh；rc 69 文件 / 212 `on` 已在镜像里（`guest-rc.txt`） |
| ② 属性服务交给 init 的 `PropertyInit`，`proppreload` 退成只读垫片或退役 | 参照系属性区 268 项；我们 rc 要写 46 个非 `ro.` 键（`guest-props.txt` ①） |
| ③ apexd 走**目录模式**（`ro.apex.updatable` 不设） | 参照系该项为空 + `/apex` 25 个 overlay；我们 6 个必需 apex 已解包（`guest-apex.txt`） |
| ④ 4 个 `/vendor/bin/hw/*` 服务先 `disabled`（或补 vendor 内容） | `guest-rc.txt`「缺失的可执行」只有这 4 条 |
| ⑤ SELinux 保持 `Disabled`，不加载策略 | 两边都 `Disabled`，参照系框架完整（`108-reference.txt` §0） |

**工期（分三段，每段有独立判据，可中途止损）**
- A-1 shadow boot 打通（PID1 切换 + 我们的编排挂回去）：**1~2 天**
- A-2 `class_start main/core` 全通、`sys.boot_completed=1`：**1~2 天**
- A-3 `pm install` + 起一个真 Activity：**1~3 天**（取决于 T1 的显示栈是否已稳定）

**风险**
1. PID1 切换牵动 T1 的全部编排（挂载顺序、adbd、harness、shim 注入点）——这是最大的一块，必须可回退。
2. `proppreload` 现在一人打三份工（属性 + NativeBridge + dnsshim），不能整块删；要拆。
3. TCG/WHPX 下 init 跑完 212 个 `on` 触发器的启动耗时未知（可能明显拖慢冷启动）——A-1 阶段就要量。
4. 我们的 `ld.config`/`linkerconfig` 目前按解包 `/apex` 走，apexd 真接管后路径可能变（要对照 `guest-apex.txt` 里 ld.config 引用 `/apex/` 的次数）。

## B｜继续 shim（为每个框架前置再造一层）

**要造的东西 = 真 init 免费给的那三块**：
- 共享属性区：268 项布局（`properties_serial` + `property_info` + 每个 SELinux context 一个文件），
  context 名表来自 `plat_property_contexts`（我们镜像里 85 KiB / 1017 条，其中 532 条是非 `ro.` 前缀）；
- trigger 引擎：212 个 `on`（含 `on property:k=*` 通配、`trigger`、`class_start`）；
- 服务管理：79 个 service 的 `restart`/`oneshot`/`disabled`/`socket`/`capabilities`/`seclabel`/uid-gid 语义
  （实测 rc 里 `user` 62、`group` 62、`socket` 38、`disabled` 38、`oneshot` 30、`capabilities` 23）。

**工期**：与 A 同量级甚至更高，且**没有上游演进路径** —— 每接一个新 framework 能力都要再补一层。
**风险（这条最实在）**：语义不全的 shim 会伪装成"源坏了"。本项目已经栽过三次
（空覆写的 `ScrollView.addView` 静默丢子树、恒 `false` 的 `Bitmap.compress`、比较写反的 `firstUrl`），
全都是"桩只返 true 不执行任务"这一类。
**B 唯一真正便宜的场景**：E1 实验证明属性区失败只是"目录/权限/重复初始化"级别的问题 —— 那时共享属性区
可以从"实现 bionic 兼容机制"降级为"照 268 项布局建文件 + 一个 socket 转发"。

## C｜复用最小框架（今天的产品形态）

数字判据（`evidence/apk-needs.txt`）：TVBox APK 引用 android/dalvik 类 **1,908** 个，其中 framework 包
**802** 个；我们的桩（`ui_stub.dex` 185 类）覆盖其中 **103** 个 ⇒ **缺 699**。
硬骨头清单里 **9 个无桩**：`Service`、`BroadcastReceiver`、`AlarmManager`、`NotificationManager`、
`Choreographer`、`HandlerThread`、`MediaPlayer`、`MediaSession`、`ActivityManager`
（`Activity`/`Application`/`ContentProvider`/`WindowManager`/`Looper`/`Handler`/`WebView` 有桩）。

⇒ **对"只跑 spider jar"：已经成立**，而且就是现在产品在用的那条路（jar + 自定义 ART 启动器 + android 桩）。
⇒ **对"宿主只做显示"：不成立** —— 显示要走的正是 Activity/Window/Choreographer 这条链，
而 APK 还引用了 `android.view.animation` 17 个、`android.text.style` 16 个、`android.view.accessibility` 16 个
这类没有桩的 UI 细节类。继续 (C) 的成本是**按包计**，不是"再补几个方法"。

## 推荐：主路 A，闸门 E1

三条都带数字的理由：
1. **文件层几乎全有**：rc 与参照系同一血统（69 vs 74 文件、79 vs 82 service、107 vs 107 setprop），
   init/apexd/secilc/app_process64 二进制运行时全在位，6 个必需 APEX 已解包，SELinux 两边都是 `Disabled`。
   ⇒ A 的阻塞点从"缺一堆东西"缩到"PID1 + 属性区"两处。
2. **B 要重写的正是 A 免费给的**（属性服务、trigger、服务管理三块，语义量见上）。
3. **C 的缺口是 699 个类 + 9 个硬骨头**，覆盖不了显示链 —— 它只适合"只跑 jar"的当前形态，不适合当终点。

**E1 是闸门**：A 与 B 都卡在"属性区为什么建不起来"。E1 只要半天、只读、不改镜像，
它的结论对两条路都必需 —— 所以先做 E1，再决定要不要动 PID1。

**闸门状态（2026-10-02 E1+E2+E3 执行后回填）**：
- E1 ⇒ **过**：属性区由 init 自己建（265 项），"建不出来"是假问题；B 在这条论据上出局。
- E3 ⇒ **过**：apexd 接受目录形态、自己标 activated，不提 loop/dm/.apex 容器。
- E2 ⇒ **判据达成（08:33）**：真 init 当 PID1 后 `getprop | grep -c init.svc` = **48→54 条**、
  `init.svc.zygote=restarting`、`ro.build.version.sdk=33` 可查；卡点已从"init/属性区"移到
  **"服务起来就崩"**（lmkd critical ⇒ 29s 重启；netd/media/mediaextractor `exited 1`）。
  过程里拔掉 11 块石头，其中**真凶是我们自己的 `propinit`**（它重建 `/dev/__properties__`、
  抹掉 init 的 `properties_serial` ⇒ 所有客户端 getprop 读空）—— ⇒ A 路线剩下的活是
  "补一套可运行的 system/vendor 内容"，不是 init 编排；E1 的"区由 init 建"就此确认。

## 第一步可验证实验（每条都写清"成功说明什么 / 失败说明什么"）

### E1｜属性区失败定因 —— **已执行（2026-10-02），结论：旧解释不成立，定因要等一次开机**

**实测证据**（本次开机的串口输出，`evidence/guest-runtime.txt` 同源，`qemu-console-art.log` 21:45:51 那次 boot）：
```
[propinit] 旧属性区已存在（非链接），先移除
[propinit] area_init(/dev/__properties__) = -1
[propinit] add ro.debuggable 失败 (rc=-1)   …（后面每条 add 都 rc=-1）
```
`/init` 第 140 行本来就在每次开机跑 propinit（`[ -x /system/bin/propinit ] && /system/bin/propinit 2>&1 | head -8`）
⇒ 这个实验**不需要 adb、也不需要改镜像**就能看到现状。

**三条分支的判定**：
1. 「私有符号解析失败」⇒ **排除**（命中会先打 `无法解析 libc 私有符号` 并 `return 2`；串口里没有，
   而且 `add` 确实被调用了 26 次）。
2. 「`area_init = -1`」⇒ **命中**（就是上面那行）。
3. 「`area_init = 0` 但 add 失败」⇒ **未命中**。

**但这条实验同时推翻了自己赖以归因的那句话**：旧代码里"旧属性区已存在（非链接）"是
**无条件打印**的 —— `readlink()` 对"目录根本不存在"同样返回 -1(ENOENT)，代码没区分。
⇒ "因为旧区已存在所以 area_init=-1"这个假设**从来没有证据**（B1 文档第 16 条、`propinit.c` 的注释都建立在它上面）。
SELinux 假设同样无支持证据：guest 与参照系都是 `getenforce=Disabled`（差距矩阵 #5）。

**已做的修正（本次提交，`blobs/propfix/propinit.c` + 重编的 `propinit`）**：
每一步都打 `errno`（readlink / remove / mkdir / area_init / add），并 `stat`
`property_info` 与 `properties_serial`；同一份输出落 **`/data/propinit.err`**（= 请求 R3，
让只读探针不必依赖 logd 也能取）。编译：108 上 NDK r27c
`x86_64-linux-android33-clang -O2 -Wall` ⇒ 0 warning，9,896 B → **11,736 B**。

**新的主导假设（待证实，不是结论）**：bionic 建区需要 `property_info`
（真机由 init 的 `PropertyInit` 从 `plat_property_contexts` 生成 —— 参照系那 268 项里就有这个 74,676 B 的文件），
单靠 `mkdir` + `area_init` 建不出来。下一次开机的 `errno` 与 `property_info` 两条会直接判掉。

**顺序调整（重要）**：新 propinit 要进镜像才读数 ⇒ 需要一次 `rebuild_gb.cmd`；而 **E2（真 init 当 PID1）
本身就会执行 `PropertyInit`** ⇒ E2 的结果同时就是 E1 的答案：
- E2 后 `getprop | grep -c init.svc` 从 0 变几十 **且** `/dev/__properties__` 有 ~268 项
  ⇒ "区由 init 建"这条链成立 ⇒ A 路线的属性区一步**免费**，B 路线可以出局；
- init 也建不出来（panic 在 `PropertyInit`/`SetupSelinux`）⇒ 那才是真前置，且新 propinit 的
  errno 会指出是哪一个。

**E1 复核结果（E2 已顺带答完，2026-10-02 06:35 实测）**：分支②"区由 init 建"成立 ——
真 init 当 PID1 后 `/dev/__properties__` = **265 项**，并且 init 自己打印
`Setting property 'ro.build.fingerprint' …` ⇒ **`__system_property_area_init` 在真 init 手里成功**，
E1 里 `propinit` 返回 -1 与"缺 `property_info`"都不是拦路石（我们的探针环境才是变量）。
⇒ **A 路线属性区一步免费；B 路线在这个论据上出局。**
唯一没拿到的读数是 `getprop` 本身 —— 它当时也吃第 7 号石头的 `execv ENOENT`（见 E2 表），
不是属性区的问题。

**当前阻塞**：`adbd` 仍起不来（`Cannot run program "/system/bin/adbd": error=11, Try again`，
桥侧 fork/vfork 拦截器把合法启动也拦了 ⇒ adb 全程 offline，属 #42 家族）。
**E2 已全程改用串口判据跑通**（`/dev/kmsg` + `<4>` 前缀），E4 的 `pm install` 判据仍然必须有 adb。

### E2｜shadow PID1 —— **已执行（2026-10-02 06:05~01:09，三十来次开机）；派单判据已达成，zygote 推到 ART 主线程**
**结论先说：机制成立，且 `init.svc.*` 从 0 变 48→54 条已实测读出（见本节末"E2 判据最终达成"）；
A 路线的"init 本身"不是墙，墙在内容层 —— 服务能起、但起来就崩（zygote `restarting`、lmkd critical）。**
工具：`tools/b1-build/shadow_init.py`（`--off` 一键回退，已实测：回退后镜像 md5 回到
`75702977759e41d985b6385969f2876d`，guest 正常起、桥在 `:18600` 监听）。
证据：`docs/research/framework/evidence/guest-e2-shadow-pid1.txt`（八段串口判据 + 每段的服务数/execv 失败数/存活秒数）。

不需要改宿主 `-append`：内核 cmdline 已经是 `rdinit=/init`，而我们的 `/init` 本来就是 PID1 ⇒
让它在看到 `/shadow-init` 标记时 `exec /system/bin/init second_stage`，真 init 顶替**同一个 PID1**，
原编排整体搬进 `/init.claw`，由 `/system/etc/init/init.claw.rc`（新增 service `clawboot`/`e2probe`）拉回。
镜像自检 12 项里 4 项专查 `/init` 的编排内容 ⇒ 用"把 `/init` 换回 `/init.claw` 的等价件"跑闸门，
**全部通过** ⇒ 证明只动了 PID1 交接、编排逐字未变。

**E2 判据最终达成（08:33，第 ㉒ 次开机）**：把编排里那句 `propinit` 跳掉之后，
派单给的判据原样读出来了 —— `getprop | grep -c init.svc` 从 **0 → 48 → 54 条**、

真凶是我们自己的 shim：`/init.claw:141` 的 `[ -x /system/bin/propinit ] && /system/bin/propinit`
会 `remove()`+`mkdir()` **重建 `/dev/__properties__`** ⇒ 真 init 写的 `properties_serial` 被抹掉
（`property_info` 74,112B 还在、`properties_serial` 不存在）⇒ 之后所有客户端 `getprop` 输出 0 行。
之前怀疑的两个方向都不成立：命名空间（`nsenter -t 1 -m` 进去读一样是 0 行，且 `nsenter 自检: 在-init-ns` 通过）、
SELinux 拒读（无 stderr）。**这条对现网也有意义**：`propinit` 与真属性区是互斥关系，不是补丁关系。
