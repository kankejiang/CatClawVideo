## 二、当前精确卡点（B1.1a）

```
[logd] Using HWComposer service: default          ← hwc 找到了
[logd] RenderEngine with SkiaGL Backend           ← 走了 GL 后端
[sf]   couldn't find an OpenGL ES implementation, make sure you set ro.hardware.egl or ro.board.platform
```

已排除：`libdrm_intel.so` 缺失（已补）、`/vendor` 命名空间不可见（已改放 `/system/lib64/egl`）、库文件不在位（adb 逐个确认）。

**下一步诊断（已部分就绪）**：
1. 让 `libpropfix` 打印 SF 的属性读取（已加 `PROPFIX_DEBUG`）—— 目前**没有输出**，说明拦截未生效或 `libEGL` 的读取没走该入口。要查：
   - `libpropfix.so` 是否真的被 SF 载入（`/proc/<pid>/maps`，趁它存活时抓）；
   - bionic 的 `libEGL` 读 `ro.hardware.egl` 用的到底是哪个入口（`__system_property_get` / `_find`+`_read_callback`）。
2. **更彻底的方案（推荐）**：**建一个真正的属性区**（bionic 提供 `__system_property_area_init` + `__system_property_add`），
   由我们自己的小工具在 `/init` 阶段初始化 `/dev/__properties__` 并写入需要的键。
   这样属性对所有进程可见（不再依赖 per-process shim），`ro.hardware.egl=mesa`、`hwservicemanager.ready=true`
   这类"跨进程约定"就都成立了 —— 也能让 SF 少加载一个 preload（`proppreload` 会遮蔽真属性区）。
3. EGL 找不到实现的另一可能：`libEGL` 的**驱动发现顺序**（`/vendor/lib64/egl` → `/system/lib64/egl`）与
   我们放的位置/命名不符；必要时补 `/linkerconfig/ld.config.txt` 的命名空间。

**下一步候选（按性价比）**：

### 六·续（第 8~13 轮，2026-10-01）

| 轮次 | 假设 | 验证方式 | 结论 |
|---|---|---|---|
| 8 | EGL 库没加载 | `dlopen`/`android_dlopen_ext` 全量日志 | **已加载成功**（`/vendor/lib64/egl/libEGL_mesa.so`）✗ 假设不成立 |
| 9 | 链接器命名空间缺 egl/hw | 读 `/linkerconfig/ld.config.txt` | 确实缺（无 permitted.paths 的 egl/hw）；已修 `ld_config_x86.txt` + init 兜底改写（实测生效）——但**仍 META-EGL** ✗ |
| 10 | 驱动不在 sphal 路径 | 用符号链接把 mesa 挂到 `/vendor/lib64/egl` 与 `/vendor/lib64`（零体积） | 加载路径已正确 ✗ 仍不接管 |
| 11 | EGL 平台/GBM 失败 | 拦截 `gbm_create_device`/`eglGetDisplay`/`eglInitialize`/`eglQueryString` | `eglGetDisplay` 返回了 display，`eglInitialize`=1，但 `eglQueryString(EGL_VERSION)` == **"1.4 Android META-EGL"**；`gbm_create_device` **从未被调用** |
| 12 | mesa 自身报错 | 开 `MESA_DEBUG/LIBGL_DEBUG/MESA_LOADER_DEBUG/EGL_LOG_LEVEL` | 日志里出现 mesa 自己的 tag（`log.tag.MESA`/`EGL-MAIN`）⇒ mesa 代码跑到了，但 dispatch 表仍是 META |
| 13 | **是我们自己的 EGL 拦截破坏了接管** | `#if 0` 关掉三条 EGL 拦截重测 | 结果不变 ⇒ **已排除** |

**最终定位**：`libEGL.so`（Android 的 loader）成功 dlopen 了 `libEGL_mesa.so` / `libGLESv2_mesa.so`，
但它的 **driver dispatch 仍是内置 META-EGL 空壳** ⇒ 零 EGLConfig ⇒ SF 退出。
问题不在路径、不在体积、不在属性、也不在我们的 shim，而在 **loader 判定"驱动可用并接管"的条件**上。

**下一步（明确的技术问题）**：查 AOSP `frameworks/native/opengl/libs/EGL/Loader.cpp` 的 `open()`：
它在 dlopen 之后要求驱动导出完整的 `egl*` 入口族并做 `eglInitialize` 校验；
mesa 的 Android EGL 是"**loader 型驱动**"（自己再去找 dri 模块），与 AOSP loader 的期望可能不同版本不匹配。
可行方向：
  a. 用与 SF 同版本的 mesa（从 Waydroid 镜像取的那份就是，但版本可能落后/超前于本 system.img 的 libEGL）；
  b. 换 `libEGL_angle.so`（vendor 里 9MB）——注意 ANGLE 默认走 Vulkan，guest 无 Vulkan 驱动；
  c. 直接把 mesa 的 EGL 入口**冒充**成 loader 期望的形态（写一层薄适配 `.so`，名为 `libEGL_<driver>.so`，
     内部转发给 mesa）——这是可控性最高的一条，代价是几十行 C；
  d. 备选：走 D3（108 上的 Waydroid）做投屏，绕过本 guest 的显示栈。

### 六·续四（第 24~27 轮：Wayland 这一跳打通）

**关键发现**：Waydroid 的 HWC（`hwcomposer.waydroid.so`）**降权/按 uid 1000 推算** runtime dir ——
实测它自己打印：
```
[logd] WAYLAND_DISPLAY: wayland-0
[logd] XDG_RUNTIME_DIR: /run/user/1000      ← 完全忽略我们传的 env
[logd] Couldn't open Wayland display.
```
⇒ 我们把 weston 改成**以 uid 1000(system) 运行**、socket 放 `/run/user/1000` 之后：
```
[astack] Wayland socket 已就绪（/run/user/1000/wayland-0）   ✔
[logd] XDG_RUNTIME_DIR: /run/user/1000                       ✔
（"Couldn't open Wayland display" / "failed to open wayland connection" 全部消失）✔
```
实现要点：busybox **没有 `setuidgid`** ⇒ 补 `/etc/passwd`+`/etc/group` 的 `system:x:1000` 条目，
用 `busybox su system -c "XDG_RUNTIME_DIR=/run/user/1000 /usr/bin/weston …"` 启动。

**同时**：`screencap` 之前失败的独立原因也修掉 —— 它跑在 adb shell(uid=shell) 下，而 `/dev/binder` 是
`crw------- root` ⇒ `Permission denied`；init 里 `chmod 666 /dev/binder /dev/hwbinder /dev/vndbinder`。

**当前唯一卡点**：链路全通（weston ✔ / binder+VINTF ✔ / allocator+mapper@4.0 ✔ / configstore ✔ /
HWC→Wayland ✔ / SF→RenderEngine(ANGLE→Vulkan→llvmpipe) ✔），但 `screencap` 仍**阻塞**（50 秒不返回 ⇒
SF 收下请求却出不了帧）。下一步查 SF 的取帧路径（线程 wchan / 是否卡在 `presentDisplay` 或 vsync 等待）。

**操作教训**：应用启动与 adb 测试必须**分成不同命令**（否则 kill 掉后台 job 会把 VM 一起带走）。

### 六·续二十五（第 60 轮：gbm/drm 探针 0 命中 ⇒ 失败在 gbm 之上）

**新增探针**（普通 C 符号 ✔）：`gbm_create_device` / `gbm_bo_create` / `drmOpen` / `drmOpenWithType` ✗
（途中修掉一个**重复函数定义** ✗ —— 更早某轮已加过 `gbm_create_device` ✗，两份导致编译失败 ✗、一直用旧 shim ✗。）

**结果**：**0 命中** ✗ —— SF 进程内 minigbm 的 mapper **从未调用 gbm/drm** ✗
⇒ 失败发生在 **mapper impl 的描述符校验 / `cros_gralloc_driver::is_supported`** 一步 ✗
（最可能是 **format/usage 组合被 minigbm 拒绝** ✗ ⇒ 直接返回 `NO_RESOURCES(5)` ✗，根本没到设备打开 ✗）。

**下一步** ✔：`cros_gralloc_driver::is_supported` 是**导出**符号 ✔（前面枚举已见 ✗）
⇒ 拦它并打印**它收到的 descriptor 与判定结果** ✗；
若确认是 usage/format 被拒 ✗ ⇒ 在 allocate 垫片里**调整 usage/format**（例如去掉 minigbm 不认的高位 ✗）
⇒ 这是目前最可能"一次打通分配"的一步 ✔。

### 六·续二十六（第 61 轮：**缺 DRI 后端** —— gbm 无处分配）

**实验：usage 掩码重试（排除 usage 假设 ✗）**
```
>> allocate(9) w=1280 h=720 fmt=0x1 usage=0x1b00 → rc=5 ✗ ⇒ 掩码 0xb00 重试 → 仍 rc=5 ✗
>> allocate(9) w=128  h=128  fmt=0x1 usage=0x300  → rc=5 ✗ ⇒ 掩码 0x300 重试 → 仍 rc=5 ✗
```
⇒ **usage 不是原因** ✗（连最小 `0x300` 也被拒 ✗）⇒ minigbm 对**任何**请求都返回 `NO_RESOURCES` ✗
⇒ 它的 **GBM 设备/后端根本不可用** ✗。

**依赖链取证** ✔：
```
mapper impl 的 DT_NEEDED：libminigbm_gralloc_gbm_mesa.so（+ libdrm.so、libgralloctypes.so…）
libminigbm_gralloc_gbm_mesa.so 未解析符号：cros_gralloc_driver::get_resolved_drm_format / get_drm_format_string
我们已打包 ✔：libminigbm_gralloc_gbm_mesa.so ✔ libgbm_mesa.so ✔ libgbm_mesa_wrapper.so ✔ dri_gbm.so ✔ libdrm.so ✔
缺失 ✗：**没有任何 `dri/` 目录、也没有 `*_dri.so` 光栅化后端**（kms_swrast/swrast ✗）
        108 的 vendor 镜像里同样没有 /vendor/lib64/dri ✗
```
⇒ **结论**：mesa 的 GBM 需要 **DRI 后端**（软件路径 = `kms_swrast_dri.so` ✗）⇒ 没有它就不能分配 ✗
⇒ 这解释了"**没有任何 gbm/drm 调用**却直接返回 `NO_RESOURCES`"✗。

取 **`kms_swrast_dri.so`** 及其依赖 ✗ ⇒ 打进 guest 的 **`/system/lib64/dri/`**（新建目录 ✗）
⇒ minigbm 的 gbm 获得软件后端 ✔（必要时配 `LIBGL_DRIVERS_PATH`/`MESA_LOADER_DRIVER_OVERRIDE=swrast` ✗）。

### 六·续二十七（第 62 轮：minigbm 支持 virtio_gpu；open 探针在 bionic 上无效）

**取证** ✔：

**两条被推翻/修正的旧结论** ✗：
