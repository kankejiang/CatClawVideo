> 目标（用户诉求）：**像真正的安卓设备一样运行，Windows 宿主只做显示**（+ 输入转发 + 原生播放）。

## 二、当前精确卡点（B1.1a）

```
[logd] Using HWComposer service: default          ← hwc 找到了
[logd] RenderEngine with SkiaGL Backend           ← 走了 GL 后端
[sf]   couldn't find an OpenGL ES implementation, make sure you set ro.hardware.egl or ro.board.platform
```

已排除：`libdrm_intel.so` 缺失（已补）、`/vendor` 命名空间不可见（已改放 `/system/lib64/egl`）、库文件不在位（adb 逐个确认）。

**下一步诊断（已部分就绪）**：
1. 让 `libpropfix` 打印 SF 的属性读取（已加 `PROPFIX_DEBUG`）—— 目前**没有输出**，说明拦截未生效或 `libEGL` 的读取没走该入口。要查：
   - `libpropfix.so` 是否真的被 SF 载入（`/proc/<pid>/maps`，趁它存活时抓）；
   - bionic 的 `libEGL` 读 `ro.hardware.egl` 用的到底是哪个入口（`__system_property_get` / `_find`+`_read_callback`）。
2. **更彻底的方案（推荐）**：**建一个真正的属性区**（bionic 提供 `__system_property_area_init` + `__system_property_add`），
   由我们自己的小工具在 `/init` 阶段初始化 `/dev/__properties__` 并写入需要的键。
   这样属性对所有进程可见（不再依赖 per-process shim），`ro.hardware.egl=mesa`、`hwservicemanager.ready=true`
   这类"跨进程约定"就都成立了 —— 也能让 SF 少加载一个 preload（`proppreload` 会遮蔽真属性区）。
3. EGL 找不到实现的另一可能：`libEGL` 的**驱动发现顺序**（`/vendor/lib64/egl` → `/system/lib64/egl`）与
   我们放的位置/命名不符；必要时补 `/linkerconfig/ld.config.txt` 的命名空间。

## 三、计划（P0 → P3，每步都有验收）

### P0（继续，1~2 天）— 把显示链路打通到"能截出图"
| 步骤 | 内容 | 验收 |
|---|---|---|
| P0.1 | 查清 EGL 驱动发现（上面 §二 的 1/2/3，优先做"真属性区") | 不再报 `couldn't find an OpenGL ES implementation` |
| P0.2 | SF 常驻 + HWC（`hwcomposer.waydroid`）接到 weston | `ps` 里有 surfaceflinger 且不退出；weston 收到 surface |
| P0.3 | 让屏幕上有内容（`bootanimation` 或一个最小原生验证程序） | `adb exec-out screencap -p` 得到**非空、可见图案**的图 |

### P1（与 P0 衔接，2~3 天）— 投屏进 Windows（= "宿主只做显示"的技术验证）
| 步骤 | 内容 | 验收 |
|---|---|---|
| P1.1 | guest 侧：SF 虚拟显示 + `MediaCodec` H.264 编码（软件编码 AVC ✔ 无需 GPU） | guest 能输出 Annex-B 流 |
| P1.2 | 宿主侧：收流 + 解码（Media Foundation）+ 上屏到现有窗口 | 窗口里看到 Android 画面 |
| P1.3 | 输入注入：宿主鼠标/键盘 → `input` 事件（或 scrcpy 式控制通道） | 能在窗口里点按 Android 界面 |

### P2（大工程，单独立项，数天~1 周）— **框架层 B1.2**
- 目标：`zygote` + `system_server` 起来，能装 APK 并启动（真 Android 应用栈）。
- 路线判断：我们这条"自编排服务栈"已到 SF，但框架需要一批 **shim 顶不了**的东西
  （**可写的属性服务**、**apex 挂载**、SELinux 策略、vintf manifest、`/data` 结构）⇒
  大概率要回到 **"真 init"** 路线（我们已具备的资产都能复用：adbd / HAL / mesa / DRM / weston / propfix）。
- 若 P0 的"真属性区"落地，P2 的难度会明显下降（属性服务是框架启动的硬前置）。

### P3（收尾，小）— 宿主播放与账号归属
- 壳给地址、宿主播（保持现状）；网盘账号/cookie 交给 Android 侧；宿主只保留显示+输入+播放。

## 四、关键决策点（需要你拍板的地方）

| # | 决策 | 选项 |
|---|---|---|
| D1 | 投屏协议 | scrcpy 式（虚拟显示 + MediaCodec + 自研接收端）／ 逐帧 `screencap`（低帧率但极简） |
| D2 | P2 路线 | 真 init 移植（推荐，目标完整 Android）／ 继续 shim（每个框架前置都造一个，可能很多） |
| D3 | 备选捷径 | 若只想尽快看到"真 Android + 宿主只显示"，可先用 **108 上的 Waydroid**（已跑通我们的 APK+数据）做投屏与集成，Windows 侧只做显示与输入；代价是需要一台 Linux 主机 |
