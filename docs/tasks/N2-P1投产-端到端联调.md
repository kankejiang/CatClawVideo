## 一、已知事实与证据（直接用 ✗）

1. **T3（`tools/waydroid-stream`）×，已入库 `2882143` ✔**：
   - 默认路线 = **`screencap` → 宿主 ffmpeg 转 CFR 30fps H.264** ✔（`-g 30` 每秒 IDR ✔）
   - 起法：`bash serve.sh -d --port 27183 --codec h264 --fps 30` ✔
   - 协议：客户端发 `CATCLAW/1\n` ⇒ 服务端回 `OK <w> <h> <codec> <fps>\n` ✔；
     帧 = `<4B 大端长度><1B 类型><payload>`，0x01 视频 / 0x02 心跳 / 0x10 触摸 / 0x11 按键 / 0x12 滚轮 / 0x00 关闭 ✔
   - **扩展**：连上 1.5s 内不发握手行的当 **raw 裸流**（供 `ffmpeg -i tcp://…` 直连 ✔）
   - 已知限制 ✔：内容**真实刷新 ~2.5fps** ✗（`screencap` 瓶颈 ✗）、jpeg 2.8fps ✗、长按无专门语义 ✗、
     接入后前 ~8 帧因缺 PPS 被跳过 ✗（**预期行为** ✔，别当 bug ✗）
2. **T2（`tools/stream-probe`）**：`H264Decoder.cs` 有未提交改动 ✗，并新增了
   `FfmpegPipeDecoder.cs` ✗ 与 `MediaFoundationH264Decoder.cs` ✗ ⇒ **两条路线都在写** ✗
   ⇒ 本任务第一件事就是**二选一定稿** ✗。
3. 我实测 T3 的**可解码性** ✔：存盘流 `ffmpeg -f null -` ⇒ **330 帧 / 11.00s** ✔（不是"不可解码" ✗，
   只是开头的 PPS 告警 ✗）。

## 二、任务（按顺序做 ✗）

  - **A｜Media Foundation** ✔：Windows 原生 ✗、无外部依赖 ✗ ⇒ **首选** ✔（H.264 是 MF 内置解码器 ✗）。

  5. 连续跑 **10 分钟**不崩、内存稳定 ✔

## 五、踩坑提醒

1. **T2 只支持 jpeg 时不要去测 h264** ✗（会得到"0 帧"的假结论 ✗ —— 我踩过 ✔）。
2. T3 的**开头 ~8 帧缺 PPS** ✗ 是**预期** ✔，不是解码器 bug ✗。
3. 坐标一定是**设备像素** ✔（1280×688 之类 ✗），不是窗口像素 ✗；HiDPI 下要乘缩放比 ✔。
4. `adb` 与"起模拟器"要**分开命令** ✗（杀后台 job 会把 VM 一起带走 ✗）—— 涉及 108 容器时同理 ✔。
5. 108 上**别人可能正在跑测试** ✗ ⇒ 用自己的端口（如 272xx ✗），**不要 `pkill` 别人的进程** ✗。
