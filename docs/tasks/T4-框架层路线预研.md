## 一、为什么单独拆这条

B1 的最终目标（"宿主只做显示"）在 **P2 框架层**才算真正达成 ✔：
现在 guest 里跑的是**自编排的服务栈**（binder 注册表、HWC、Composer、ANGLE… 都通了 ✔），
但**没有 zygote / system_server** ✗ ⇒ 装不了也起不了普通 APK ✗（我们的 TVBox 也是靠自定义 ART 启动器跑的 ✗）。

**难点清单（已知的"框架前置"）**：
| 前置 | 现状 | 备注 |
|---|---|---|
| **可写的属性服务** | ✗ | 我们的 `proppreload` 是 **per-process 编译期表** ✗；`propinit` 想建**真属性区**失败 ✗（`__system_property_area_init` = -1，疑因缺 **SELinux 策略** ✗）⇒ 而 framework 大量**读写**属性 ✗ |
| **apex 挂载** (`apexd`) | ✗ | system 镜像里 framework 类库大量在 `/apex/com.android.*` ✗ |
| **SELinux 策略** | ✗ | 属性区/服务注册/文件上下文都依赖它 ✗ |
| **VINTF / compatibility matrix** | 部分 ✔ | 我们已手工合并 manifest ✔；但 framework 侧要求更多条目 ✗ |
| **`/data` 结构与 dalvik-cache** | 部分 ✔ | guest 有 `/data/catclaw`、`/data/dalvik-cache` ✗（启动日志里报过 oat 目录缺失 ✗） |
| **init 的职责**（lazy HAL、service 管理、`on boot` 触发） | ✗ | 我们没跑真 init ✗（lazy HAL 循环就是这么来的 ✗） |
| **binder 三实例 / servicemanager / hwservicemanager** | ✅ | 已通（T1 的成果 ✔，可直接复用 ✔） |
| **GL / HWC / Composer** | 部分 ✅ | ANGLE→Vulkan→lavapipe 通 ✔；HWC 回调路径仍在收敛 ✗（T1 在做 ✗） |

## 二、目标（可验收）

产出一份**决策级**预研，包含四件东西：

1. **差距矩阵（证据化）**：每一行给出"框架需要的某前置" ↔ "我们 guest 的现状" ↔ **证据**
   （证据必须是**可复现的观测**：镜像里的文件路径/大小、命令输出、镜像构建脚本里的对应逻辑等 ✗ 不要写"大概没有" ✗）。
2. **三条路线对比 + 推荐**：
   - **(A) 真 init 路线**：移植/裁剪 Android init（fstab/apex/SELinux/属性服务）到 guest ⇒ 目标完整框架；
   - **(B) 继续 shim 路线**：为每个框架前置再写 shim（属性服务、apexd 替身、SELinux 关闭路径…）；
   - **(C) 复用最小框架**：不做完整框架，只让**我们的 ART 启动器 + 有限 UI 桩**跑（当前状态 ✗）能否满足
     "宿主只做显示"（判断依据：**TVBox APK 到底需要 framework 的哪些部分** ✗ —— 需给出证据 ✗）。
   每条给出：需要改什么、预估工期、风险、**第一步可验证实验** ✗。
3. **探针清单**：一组**只读/低风险**的探针（见下文 §四），每条的**预期观测**与**判读规则** ✗。
4. **工期与并行建议**：与 T1/T2/T3 的依赖关系 ✗（哪些能在框架层没通之前先做 ✗）。

**验收**：文档里每一行差距都有证据链接 ✔；推荐路线给出"第一个实验是什么、成功/失败各说明什么" ✔；
探针脚本能跑（至少能对**镜像**做静态检查 ✔，不要求改 guest ✗）。

## 四、建议的探针（只读/静态，先做这些）

1. **APEX 审计**：解析 system 镜像，列出 `/apex/**` 与 `/system/apex/**` 里**必需**的 APEX（art/i18n/conscrypt/os.statsd… ✗）
   与实际**存在**的对照 ✗ ⇒ 结论：framework 启动需要挂载哪些 ✗。
2. **framework 类库审计**：`framework.jar`/`services.jar` 的路径与大小 ✗（我们镜像里 `/system/framework/**` 有什么 ✗）。
3. **init rc 审计**：统计 `/system/etc/init/*.rc` 里 `service`/`on boot` 的数量与类别 ✗
   ⇒ 结论：**真 init 路线需要落地多少配置** ✗（给出量级 ✗）。
4. **属性依赖审计**：从 `init.rc`/`*.rc` 里抽取框架启动**必需**的属性名 ✗（例如 `ro.zygote`、`dalvik.vm.*`、`persist.sys.*` ✗）
   ⇒ 与 `proppreload` 的 161 条表**求差集** ✗ ⇒ 结论：属性服务**必须**可写吗 ✗（哪些是只读 ✔ 哪些要写 ✗）。
5. **SELinux 依赖审计**：`/system/etc/selinux/**` 是否存在 ✗、`__system_property_area_init` 失败是否因它 ✗
   ⇒ 结论：**关掉 SELinux 能否绕过** ✗（在 AOSP 代码路径上给依据 ✗）。
6. **dalvik/oat 审计**：guest 启动日志里 "Dalvik cache directory does not exist" ✗ 的影响面 ✗
   ⇒ 结论：`/data/dalvik-cache` 需要满足什么条件 ✗。
