## 二、已修的三处缺陷（含根因与证据）

### 缺陷 1：ART verifier 拒绝壳的类 —— 磁力播不了的第一层根因

**现象**：`playerContent` 恒在 2ms 内失败：

```
VerifyError: Verifier rejected class com.github.catvod.spider.ProxyOrigin:
  void getan() failed to verify: [0x192] register v4 has type
  Reference: android.graphics.drawable.Drawable but expected
  Reference: android.graphics.drawable.Drawable
调用栈：WoGG.playerContent → Pan.playerContent → ProxyOrigin.getan
```

**根因**：桥的 UI 桩 `ui_stub.dex`（桩优先加载器）把 **值类 `android/graphics/**`** 也塞了进去。
于是 spider 代码里的 `Drawable` 解析成**桩 Drawable**，而它调用的真 framework 方法签名
（`Activity.getWindow().setBackgroundDrawable`）里的 `Drawable` 来自 **boot classpath**
→ 同名不同类 → verifier 拒。

**修复**：`JavaBridge/qemu-src/tools/build_gb_dex.py` 的 `build_ui_stub_dex()` 排除 `android/graphics/`。
（UI 事件类 Dialog/Toast/View 仍保留；值类在 guest 里本就有真实现。）

**证据**：修复后同一条线返回真实可播地址（`ok:true`，2103ms）：

```
[srv-resp] 玩偶.playerContent ← {"parse":0,"jx":0,"url":"http://127.0.0.1:6678/proxy/play/夸父盘/怪屋/4k.mp4"}
[srv-resp] 新6V.playerContent ← {"parse":0,...,"url":"magnet:?xt=urn:btih:241276a04e77cd0f5c1f90cbbfececf5f7169da6…"}
```

> 附：试过 `-Xverify:none`，**无效**（确认已传给 ART 仍被拒），故未采用，init 里该标志待清理。

### 缺陷 2：无头 guest 没有 Activity

**现象**：能跑起来的源也报

```
NullPointerException: Attempt to invoke virtual method
  'android.view.Window android.app.Activity.getWindow()' on a null object reference
  at com.github.catvod.spider.ProxyOrigin.getan(Unknown Source:177)
```

**根因**：壳经 `ActivityThread.mActivities` 取 Activity；guest 不是 zygote 起的，桥注入的是**空 ArrayMap**
→ 恒为 null。

**修复**：
- 新增 `JavaBridge/guest-src/bridge/FakeActivity.java`（真 `Activity` 子类，覆写 `getWindow()`）+ `FakeWindow.java`
  （按 guest framework **API33** 的 53 个抽象方法逐一空实现，带调用日志；方法集由
  `guest framework.jar` 反汇编得到，`build.cmd` 里 guest 补充类改用 `platforms\android-33\android.jar` 编译）。
- `Art.injectActivityThread()` 里把一条 `ActivityClientRecord{activity=FakeActivity}` 塞进 `mActivities`。

**踩坑（已规避）**：`attachBaseContext()` 会碰 autofill 注册 NPE → 改反射填 `ContextWrapper.mBase`；
`new Binder()` 在 guest 无 native 实现 → 用普通对象做 ArrayMap 的 key。

### 缺陷 3：init 丢失「迅雷段」—— 磁力点了完全没反应

**现象**：UI 点了磁力条目后**无声无息**（没有播放、也没有报错弹窗），bt.log 每 3 分钟一条：

```
外部 VM 已启动，但 180s 内迅雷 harness 未回连控制端
[磁力展开] 探测无果：全集打包.1080p.HD国语中字无水印.mkv
```

**取证**（guest 调试后门）：
- `/proc/cmdline` 有 `thunderport=18080` → 合并模式已开；
- `/harness`、`/qemu-aarch64-static`、`/thunder-arm/` 都在位；
- `ps` 里**没有 harness 进程**，`/thunder.log` 不存在；
- `grep -c thunder /init` = **0** → **`/init` 里没有拉起 harness 的迅雷段**。

**根因**：迅雷段本由 `build_bootimg_inject.py` 在注入 boot image 时一并打入；我的重建管线
（`inject_dex.py`，只换 `gb.dex`/`ui_stub.dex`/`init`）用的 init 是**合并迅雷之前的旧版**。

**修复**：按注入器原文把迅雷段插回 `/init`（脚本 `.zwork/patch_thunder_init.py`），重新打包部署。

**证据**：

```
ps: 166 0  /qemu-aarch64-static -L /thunder-arm /harness
/thunder.log: [proxy] ✅ 监听 0.0.0.0:20080    [main] 进入事件循环（控制端口 18080）
bt.log:      [02:12:21.317] 外部 VM 就绪（ART VM 媒体口 18601，迅雷 harness 已回连）

### 附带修复（不影响播放，但会刷屏）

桌面桩 `android/os/Process.java` 的 `myPid()` 改用 `/proc/self/stat`；`bridge/Server.java` 的
父进程看门狗也加了容错。

## 六、2026-09-30 复测：后续链路的真正断点在宿主侧（已修，无头实测 10/0 与 11/0）

> 本节由复测接手人补写。结论先说：**三处缺陷的修复都有效，但「点了磁力没有下文」还剩第四个断点**
> ——合并 VM 会把爬虫桥打死。现在也修了，并有端到端字节证据。

### 6.1 新根因：迅雷段把 ARM 库路径泄漏进 init 环境 → artlaunch 起不来

现网 `/init` 的迅雷段里有 `export LD_LIBRARY_PATH=/data/catclaw/art/lib:/thunder-arm/system/lib64`，
而这段**跑在 artlaunch 之前**，于是 x86 的 artlaunch 去 ARM sysroot 找库：

```
[init] binfmt arm64 已注册
[thunder] harness 监督循环已起（CTRL_PORT=18080 BLK_DEV=/dev/vda，日志 /thunder.log）
CANNOT LINK EXECUTABLE "/system/bin/artlaunch": "/thunder-arm/system/lib64/libdl.so"
        is for EM_AARCH64 (183) instead of EM_X86_64 (62)
[init] 桥进程已退出，退出码=1
```

应用侧时间线（10:49 会话，`home-debug.log`）实锤同一因果链：
`合并迅雷：ART VM 正按纯桥配置运行 —— 重启为合并配置` → `等不到 guest 桥（端口 18600，超时）`
→ `桥进程已退出，退出码=1` → **`[home] 首载失败（候选 47 站，耗时 19123ms）`** → `桥预热失败/放弃`。
即：**点一次磁力 = 重启成合并配置 = 整个爬虫桥死亡**，之后任何站点调用都没有下文——这就是报告开头
那句「spider 返回 magnet 之后就没有下文」的宿主侧断点（不是磁力链路本身坏了）。

**修法**：ARM 库路径只挂在 harness 那一条命令上（子进程环境），并在 artlaunch 前把
`LD_LIBRARY_PATH` 复位成 x86 三目录。三处同步改，缺一处下次重打就长回来：
现网 `x86guest\art_initrd_x64.gz`（脚本 `.zwork/fix_thunder_env_leak.py`，原件备份
`.bak-armenv`）、注入器模板 `JavaBridge/qemu-src/tools/x86guest/build_bootimg_inject.py`、
`.zwork/patch_thunder_init.py`。

### 6.5 再往下追两层：退出播放页重开必失败 + 代理短读断流（2026-09-30 上午补）

跑 T5（10 分钟连续读 + 中途退出再进）时又挖出两层，都在宿主侧：

**A. 「退出播放页 → 再进同一片」100% 失败，报成「磁力无资源」**
链条：首解时 `ListFilesAsync` 的任务名取自磁力 `dn`；会话被 `Teardown` 结束后 `_history` 清空，
重开时 `TryOpenAsync(preferName=集名)` 会**换一个任务名**再发一次 TASK MAGNET
（实测首解用 `成名在望.mp4`、重开用 `01-1080p-HD国语中字…mkv`）。同一 btih 在迅雷里只有一份，
新任务起来了但**种子永不落盘** → 宿主 46s 超时。
就算复用原任务名（新增 `_resolved` 解析缓存：任务名/目录/文件列表/种子路径，随 VM 生死作废），
重发 `DL` 仍秒撞 `st=9128 BT 下载任务创建失败` —— `Teardown` 发的 STOP 清不掉引擎里的任务句柄
（guest 侧 stopTask 的老问题，下载路径早有 `SendDlWithRecoveryAsync` 兜，**播放路径一条兜底都没有**）。
修法是同一招：撞 9128 → 重启 harness（进程一没任务表就空；`/thunder-data` 是 VM 级 tmpfs，
种子与已下数据都不随进程死）→ 重发 DL。
实测（`magnet-check … reopen`）：`复用已解析种子（不再发 TASK MAGNET）` → `st=9128` →
`harness 已重启并重新回连` → `播放地址已就绪` → `拉流验证通过 HTTP=206 65536B 头=1a45dfa3`，
**R1 46.0s 恢复、R2 立刻出数据，11 通过 / 0 失败**。
⚠ 中途我自己引入又当场修掉的一个：恢复分支清了 `s.DlSent` 没再置回，而 `OnReport` 靠 `DlSent`
区分「阶段一 play=种子路径」与「阶段二 play=视频地址」，结果第二条 play 被当种子路径吞掉、
`Played` 永不为真，白等 240s —— 现在 `DlSent = true` 放进循环里每次下发前都设。

**B. 代理「请求位被窗口甩下」立刻 break = 响应体短于已声明的 Content-Length**
`ServeAsync` 里 `if (pos < baseNow) break;`：自己刚 `Recenter(first)` 之后 `_base` 要等上游循环真的
搬过去才更新，那一轮采样到的还是上一次 seek 的旧窗口（实测 124.9MB），于是**第一块就断**。
播放器视角就是「放着放着中断」。改法：给它与断粮同样的 60s 预算（期间每 ~2s 再踢一次 Recenter），
超预算才按「窗口被别的读者抢走」结束。T5 已按这条复跑并通过（见下面 C）。

**C. T5 长跑结论（2026-09-30，§6.5 全部条目修完 + 台架按播放速率节流之后）**

`magnet-check … t5`：**10 通过 / 0 失败** ——
`T5 连续读满 10 分钟不卡死 ⟵ 10.0min 读了 101.0MB（2,377 块，平均每块 43.5KB，最慢单块 0.0s，重开 1 次）`。
「重开 1 次」= 第 3 分钟 `engine.Stop()` 模拟退出播放页后再 `TryOpenAsync` 回到同一片
（走 A 的复用 + 9128 恢复路径），之后连续读完两集共 3 轮，全程没有一次 >60s 无数据。
同一轮里 `R1 退出会话后能重开同一片 = 46.0s`、`R2 重开后立刻取得首块数据 = HTTP 206 65536B`（reopen 单跑 11/0）。
⚠ 台架读法必须**按 ~1.2MB/s 节流**：块设备秒供路径下不节流会在十几秒内把 250MB 读满 8 轮，
测到的是磁盘带宽而不是「连续播放不中断」（第一版就是这么测的，数字见下面的 49 万请求那条）。
⚠ 那条「每请求只吐 ~100 字节」的效率问题已查到根因并修掉（是真 bug，不是台架噪声）：
`ServeAsync` 开头 `first = Math.Min(start, _totalSize-1)` + `if (last < first) last = first;`
—— 请求起点一旦**越过文件尾**（引擎实际文件大小比种子报的小一点就会这样），它不报「到底了」，
而是把请求夹成**一个字节**、偏移永远不动；客户端按 `Content-Length` 读就原地死循环。
实测同一个 `GET bytes=261897401-261897401` 重复约 **29 万次**（250MB 的片共发 490,953 个请求）。
修法：越界请求直接回 `206 + Content-Length: 0`（不回 416 —— Cues 那段 A/B 已证明 416 会让 FFmpeg 弃流）；
另补「上游 EOF 而请求位仍在文件内」时重新武装上游（旧代码一律 break 成短读）。
修后同一台架同一部片：**1,975 个请求、平均每块 126.1KB**（原 49 万 / 0.5KB），
收尾一条 `请求起点 254829236 已在文件尾（共 254829236B）之外 → 206 空体收尾` 即止。

### 7.1 根因（每层都有反例，不是猜的）

1. **宿主改写只认字面量 6678**。壳的流服务端口会顺延（同 guest 里先后装载过 Guard 壳），
   于是 `127.0.0.1:6679/proxy/play/…` 整条不被改写 → 播放器直接连**宿主回环**的 6679（没人听）→ -138。
   改：`JavaSpiderRuntime.RewriteShellStreamPorts`（`CatClawVideo.Maui/Providers/JavaSpiderRuntime.cs:543`）
   把任意 `127.0.0.1:<p>` 的 `/proxy/play/` 换成宿主隧道端口，并用 **`?gp=<p>`** 把真端口捎给 guest 桥。
2. **壳自报的端口会说谎**。一个 guest 里装着 N 个 Guard 壳就有 N 个流服务（`netstat` 实测
   `6678 6679 6680 6681 6682 6683 6684 6685` 全在听），壳的 `adjustPort` 是「从 6678 往上扫，
   谁应答就用谁」—— 它扫到的是**别的壳**的应答。逐端口探同一个播放路径的实测：
   `6679…6685 connect 成功但 recv 0B`，只有 **6686** 回 `HTTP/1.1 200 + Content-Range`。
   ⇒ 光把 `gp` 透传还不够。改：`bridge.Art.streamPassThrough`（`JavaBridge/src/bridge/Art.java`）
   按 **① `gp` ② 上次应答过的缓存端口 ③ 66xx 段并行扫描** 选路，判据是「谁对这个 path 真的回 HTTP 头」；
   响应头与 body **原样过桥**（206/Content-Range 不重构，播放器 seek 语义不变）。
3. **壳的流 handler 依赖 `User-Agent`**。裸 socket 手拼请求（不发 UA）时，壳在
   `merge.aF.i` 里 `String.contains(...)` on null **NPE**，**13ms 就挂断、一个字节都不回** ——
   看起来和「僵尸壳没应答」一模一样，白跑了两轮判据。旧实现走 `HttpURLConnection`，它自带
   `User-Agent: Java/17`，所以这个依赖从没暴露过。补 UA（+`Accept-Encoding: identity`）后同一请求
   变成 `200 / 407ms / 65536B`。

### 7.5 毒化收敛（已修，15:50–15:56 端到端实测）

**症状**：点一次没登录的盘（优汐盘），整个网盘源以后再也不响应 —— 实测 14:09 那条
`playerContent(优汐智1)` 之后，14:14 / 14:19 / 14:24 同站的 `homeContent`、`categoryContent`、
`detailContent` **连着三条都撞 300s 看门狗**。

**根因两层**（都在 guest 桥里）：
1. `Server.call` 用 `synchronized(SITE_LOCKS[…])` 串行同站调用，而壳内的网盘请求**没有读超时**
   ⇒ 一条 hang 死的调用**永久**持有该站锁，后来的调用无期限排队。
2. `CALL_POOL` 是 `newFixedThreadPool(4)` ⇒ 每条 hang 死的调用吃掉一条池线程，
   **4 次就把整条桥（连别的站点）一起堵死**。

**修法**：`Server.call` 改 `ReentrantLock.tryLock(10s)`，拿不到锁立刻回人话错误
（`站点 X 上一次调用仍未结束（网盘线路无响应，通常是那个盘没登录）——请稍后重试或换线路`）；
`CALL_POOL` 改 `newCachedThreadPool`（daemon 不变），让泄漏的线程只毒化它自己那一站。

**实测（`_scratch_tb/gp-check/poison_test.py`，顺序：hang → 同站 → 他站）**：

| 步骤 | 修复前 | 修复后 |
|---|---|---|
| `playerContent(优汐智1)`（未登录） | 300s 无响应 | 303s 无响应（这条本来就没救，看门狗照旧） |
| 紧接同站 `玩偶.homeContent` | **再撞 300s**（14:14/14:19/14:24 三条实测） | **11s**（桥内 10001ms = tryLock 到点）回 `ok:false + IllegalStateException: 站点 玩偶 上一次调用仍未结束…` |
| 他站 `seed.homeContent` | 单条 hang 时还能跑，第 4 条起全堵 | **2s `ok:true`** |

宿主侧不用改：`CallAsync` 把桥的 `error` 原样拼进异常（`JavaSpiderRuntime.cs:1004`），
所以这句话直接进播放页的「解析失败」文案 —— 用户看得到原因，也不再被 300s 静默。
⚠ 台架判据的小坑：桥回的是 JSON，中文全是 `\u` 转义，**先反转义再断言**（踩过一次，误报 False）。

## 八、2026-09-30 傍晚：为什么每次重启都不回到上次那个站点（已修，实测）

### 8.1 先排除“没记住”

`%LOCALAPPDATA%\CatClawVideo.Maui\CatClawVideo.Maui\Settings\preferences.dat`（941B）里明确存着
`home_preferred_site":"\u73A9\u5076"` ⇒ **写入是好的**（`HomeViewModel.SelectSiteAsync:226`），
启动也确实用了它：`[home] 首选 key=玩偶 命中=👽玩偶哥哥┃4K弹幕`。

### 8.2 真正的断点：首屏比爬虫桥先跑，失败被 `catch {}` 吞掉

修前的 12 次启动日志（同一台机器）每一次都是同一个落点：

```

…（13:35 / 13:58 / 14:26 / 14:43 / 14:54 / 15:03 / 15:09 / 15:25 / 15:44 / 15:59 / 16:08）
16:08:11.715 [home] 首载 site=🗂我的云盘┃配置 分类=2 耗时=11881ms
```

加了留痕之后一次就抓到原因（16:25 那次启动）：

```
16:25:38.147 [home] 首选 key=玩偶 命中=👽玩偶哥哥┃4K弹幕
16:25:42.756 [home] 首选 👽玩偶哥哥┃4K弹幕 第 1 次取分类失败：InvalidOperationException: ART guest 起不来（详见 [art-vm] 日志）…

```

⇒ jar 源的取数路径在 VM 冷启时是**快速失败**（不等待就绪），而 `HomeViewModel` 里那句
`catch { }` 把异常连同原因整条吞掉，直接走「并发探测兜底」——探测赢家每次都是最快应答的
`MDrive`（🗂我的云盘┃配置），而且它也是 jar 源，所以看起来像「记住了网盘站但记错了」。

### 8.3 修法与修后数字

两层都改了（先加留痕抓到原因，再把原因本身修掉）：
- **运行时层（根因）**`JavaSpiderRuntime.EnsureBridgeAsync`：`ConnectAsync` 返回 null 时不再当场抛
  「ART guest 起不来」，而是**等 2s 重试（最多 2 次）**再报错 —— null 的含义是「另一路正在拉 VM，
  本轮让位」，不是「起不来」。
- **UI 层（兜底）**`HomeViewModel.LoadHomeAsync`：首选站点取分类改为 **留痕 + 有界重试（5 次 × 4s）**，
  全失败才回退探测。

同一次冷启动（16:30，运行时层修好后）：

16:30:26.521 [art-vm] guest 桥就绪 127.0.0.1:18600
16:30:28.658 [home] 首载 site=👽玩偶哥哥┃4K弹幕 分类=8 耗时=14739ms
```

| | 修前（12 次启动恒定） | 修后 |
|---|---|---|
